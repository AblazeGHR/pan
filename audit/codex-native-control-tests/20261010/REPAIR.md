## Production race, proof and uncertainty

The first commit edits only TerminalRunner.input in production. `_TrackedCall._work` publishes `_done` as its last operation; Python thread teardown may still be alive after publication. The next input previously called reset, whose live-thread guard raises RuntimeError; IPC maps it to handler-error. Creating a new call after prior work completes keeps independent results and avoids that guard. The input reservation is occupied before Thread.start, closing a second window where a concurrent input could replace an unstarted call's payload. In-flight writes still refuse with busy; no duplicated write/retry, widened timeout, swallowed exception or weakened cleanup.

`tests/test_terminal_tracked_call.py` forces completion-before-thread-exit, reservation-before-start, and blocked in-flight write. `test_detach_completed_write_before_thread_teardown` forces only Thread teardown to linger around real ConPTY writes and named-pipe IPC, and runs original detach assertions. On baseline production this real-OS regression yields exactly the historical `RunnerClientError: handler-error` (`race-real-before.txt/xml`). Deterministic unit tests fail on baseline (`race-before.txt/xml`) and pass after repair; real-OS regression passes after repair (`race-real-after.txt/xml`). These establish the discovered production defect and its repair. Historical full-run log did not retain inner handler diagnostics, so exact attribution of that specific historical occurrence remains unproven; repeat and full validation constrain current stability, not universal OS behavior.
