# 目标与范围

> 讨论顺序第 1 步：方向和边界。

---

## 1. 愿景

CLIConductor 是一个让用户**全方位、可远程地管理和对话本地 Agent CLI** 的工具平台。通过 Meta-Agent 实现多 Worker 的高级别调度，让 Agent 擅于闯入各个场景（开发、社交、日程、自动化……）。

| 借鉴项目 | 借鉴点 |
|----------|--------|
| OpenClaw / Claw | 本地化 + 路由方案；AI 闯入本地管理与社交平台 |
| Tutti | 跨 CLI 工作；统一界面和 Adapter 设计 |

## 2. 边界

| 做 | 不做 |
|----|------|
| CLI Agent 调度器 | 不自己实现 AI Agent |
| 进程管理 + 消息路由 + 通道适配 | 不管理 Worker 的工作目录内容（git、文件编辑） |
| Session 可检索（摘要/标签/搜索） | 不做通用知识库 |

## 3. 核心场景（按优先级）

| 优先级 | 场景 |
|--------|------|
| P0 | Web Dashboard 远程管理、Meta-Agent 调度、QQ Bot 通道 |
| P1 | 多 CLI 适配（cbc / claude-cli / gemini-cli）、Worker 快速包装为专用 Agent、远程访问 |
| P2 | 自动化流水线（定时/事件驱动） |

## 4. 定位结论

| 决策 | 结论 |
|------|------|
| 与 CLI 工具关系 | 多 CLI 支持，Adapter 模式是核心设计 |
| QQ Bridge | 一等通道，与 Dashboard 同等重要 |
| 多用户 | 暂不，但架构预留扩展点 |
| Session 数据模型 | cbc 专有字段移入 `adapter_config`，Session 只保留通用字段 |
| 通道可见性 | 支持隔离能力。最高权限用户拥有一切数据的可视权和交互权。受限通道（如对外 QQBot）可限制其 Worker 权限（不可 spawn、不可创建 Session、不可访问工作目录外） |
| 远程认证 | 需要认证 + 来源辨析（如按 QQ 号区分用户 vs 外人） |
| 事件协议版本化 | 留到模块设计阶段定义 |

## 5. 模块拆分

### 5.1 原则

1. 每个模块独立开发、独立测试、独立部署
2. 模块间通过 HTTP/WS 接口通信，不 import 彼此内部实现
3. Core 最小化：只做进程管理 + 消息路由
4. 通道是插件

### 5.2 架构图

```
                     ┌──────────────────────┐
                     │    通道层 (Channels)   │
                     │ Dashboard / QQ Bot    │
                     │ Meta-Agent / 更多...   │
                     └──────────┬───────────┘
                                │ HTTP / WebSocket
                     ┌──────────▼───────────┐
                     │       核心层 (Core)    │
                     │ Session / Worker      │
                     │ Event Router          │
                     │ Adapter Registry      │
                     └──────────┬───────────┘
                                │ Protocol
               ┌────────────────┼────────────────┐
               │                │                │
     ┌────────▼───────┐ ┌──────▼──────┐ ┌───────▼──────┐
     │  Adapters      │ │  Memory     │ │  SDK         │
     │  cbc/claude/.. │ │  摘要/标签  │ │  Worker 包装  │
     │                │ │  知识沉淀   │ │              │
     │                │ │  偏好记忆   │ │              │
     └────────────────┘ └─────────────┘ └──────────────┘
```

### 5.3 模块职责

| 模块 | 职责 | 对 Core 的依赖 |
|------|------|---------------|
| **Core** | 进程生命周期、Session 持久化（原始数据）、事件路由、Adapter 注册 | — |
| **Memory** | Session 摘要/标签/搜索、跨 Session 知识沉淀、用户偏好记忆 | Core WS 事件流 |
| **Adapters** | 每种 CLI 一个 adapter（启动参数、事件解析、消息编码）| Core 协议 |
| **WebChannel** | HTTP 服务 + Dashboard 前端 + Meta-Agent WS | Core HTTP/WS |
| **QQChannel** | QQ Bot，将 QQ 消息转为 Core 任务 | Core HTTP/WS |
| **Remote** | 远程隧道 + 认证 + 来源辨析 | 通道层 |
| **SDK** | Worker 快速包装为专用 Agent | Core HTTP/WS |

**Core 与 Memory 的分界**：Core 只存原始数据（history 数组），不索引不加工。Memory 监听 Core 事件流，生成摘要/标签/知识，暴露自己的 API。

### 5.4 模块通信

所有模块通过 Core 暴露的 HTTP/WS 协议通信，不 import Core 内部实现。每个通道是 Core 的一个"客户端"。

```
POST /api/sessions          → CRUD Session
POST /api/spawn             → 启动 Worker
POST /api/task              → 发任务
WS   /ws                    → 事件流（广播）
WS   /ws/agent              → Meta-Agent 专用
```

### 5.5 跨平台

当前约 30 行 Windows 特化代码，不单独拆模块。改造方案：`taskkill` → `psutil`，`powershell` → `sys.platform` 分派，CLI 路径 → 配置化。

## 6. 迁移路径：单仓渐进

```
现在                    Phase 1             Phase 2              Phase 3
src/                   packages/core/      packages/core/       packages/core/ (稳定)
├── server.py  ──→     ├── 内部清洁化        ├── API 稳定          packages/adapters/*
├── worker.py          └── 暴露 API         packages/adapters/    packages/memory/
├── session.py                              packages/memory/     packages/qq/
├── config.py          qq-bridge/           packages/qq/         packages/web/
├── adapters/          (不碰)               packages/web/        packages/remote/
                                              ↑ 各通道独立迭代    packages/sdk/
ts/app.ts                                                        ↑ 目标达成
```

| Phase | 内容 | 关键交付 |
|-------|------|---------|
| 1 | 清洁 Core：内部重构，外部只走 HTTP/WS；移 cbc 字段到 `adapter_config` | 稳定的 Core API 契约 |
| 2 | 逐个抽离通道：QQ → Web → Memory → Remote → SDK | 各模块独立目录 |
| 3 | 所有模块独立迭代 | 架构目标达成 |
