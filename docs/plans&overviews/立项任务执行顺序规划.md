## 二、依赖关系

```
C1（Monitor 测试）────── 独立 ──────────────┐
                                           ├──→ D（skill 手册需引用 C 结果 + B 定型）
B1+B2（报告链路+订阅）─── 依赖已合入的 ma-role ┤
   │                                        │
   └──→ B3+B4（watchdog + handoff，依赖 B1）┘
          └──→ B5（MCP 隔离，最后）

A1+A2（worker.py 修复）── 与 B1 都动 worker.py → 不并行，错峰
```

**关键约束**：
- **A 与 B1 都改 `worker.py` → 不能同时开**（文件冲突）
- B3 依赖 B1（watchdog 扫落盘队列）
- D 依赖 C 结果 + B 定型（skill 手册要写准确的完成通知方式）
- B5 最后（要 role+managed 全就位）

## 四、并行汇总（供 assign）

| 批 | 任务 | 冲突风险 |
|----|------|---------|
| 批 1（现在）| **C1 + B1+B2** | 无（C 纯测试，B1 独立区）|

## 五、模型与监督

- 模型：默认 `ds-v4-flash` + effort auto；复杂任务（B1 报告链路、B3 watchdog）可升 `ds-v4-pro`
- 监督：`/ws/agent` 事件驱动（Monitor）+ 报告订阅二选一（见 Worker监督文档）
- 合并：每个 worker 完成后检查提交，**合并经用户批准**
- 工作树：每任务独立 worktree（`d:/project/<task>`），避免冲突

## 六、操作端口约束（2026-08-16 教训）

**MCP pan server 固定连 8768（main 服务）；pan-test 服务在 8767。**

- **操作 pan-test 服务的 worker（批 2+）：必须用 HTTP API（`http://127.0.0.1:8767`）**——创建 session、spawn、assign、删除
- **用 MCP 工具（`mcp__pan__*`）操作的是 8768（main）**——只用于 main 服务的 session/worker
- 协调失误实例（2026-08-16）：批 2 用 MCP 工具建 session 落在 8768，worker 跑错代码 + Monitor（连 8767）收不到事件
- Monitor 脚本支持 `PAN_WS_URL` 环境变量指定监听端口（默认 8768）
- 注意 worker id 在 8767/8768 各自独立编号
