# 统一服务端消息队列改动计划

状态：设计稿，未实现

日期：2026-09-01

## 1. 目标

将前端“待发送”和服务端 `Session.queue_pending` 合并为同一个服务端权威队列。

目标行为：

- 用户消息在发送确认前，必须已经持久化到服务端队列。
- 前端不再维护一份具有业务语义的本地待发送队列。
- 前端列表中的每一项与服务端队列中的每一项使用同一个 `queueItemId`。
- 用户消息、Agent 消息、完成报告和 QQ 提醒可以出现在同一条有序队列中。
- 队列项必须标记来源，例如 `user`、`report`、`qq`、`agent`、`system`。
- 只有 `source=user` 且尚未被 Worker 接管的项允许编辑。
- 所有尚未被 Worker 接管的项都可以调整顺序和删除。
- Worker 重启、网络重连和前端刷新不能产生第二份同内容消息或重复执行。

本计划只描述统一队列的改造方案，不包含本文件提交时的代码实现，也不改变当前运行中的服务。

## 2. 当前实现和问题边界

当前实现存在两层不同性质的队列：

| 队列 | 位置 | 当前职责 | 问题 |
|---|---|---|---|
| 前端发送队列 | React `queueStore`，并持久化到 `pan.sendQueue.<sessionId>` | Worker 忙时暂存用户文本，支持编辑、排序、删除 | 不是服务端真源，刷新、换设备和多端不一致 |
| 服务端持久队列 | `Session.queue_pending` | task、report、QQ 等持久化投递 | 前端只能看到部分项，且历史上不同来源的结构不统一 |
| Worker 信号队列 | `Worker.pending_signal` | 唤醒 Worker 消费者 | 只应保存唤醒信号，不应成为正文真源 |

当前用户消息的典型路径是：

```text
Worker 忙
  → 前端 localStorage 待发送队列
  → Worker 变 idle
  → WebSocket user_inject
  → Session.queue_pending / Worker 信号
  → Worker 执行
```

目标路径是：

```text
用户输入
  → 服务端生成 queueItemId 并持久化
  → 返回“已入队”确认
  → 前端展示服务端队列镜像
  → Worker 按服务端顺序 claim
  → 执行成功后完成消费
```

重要边界：`pending_signal` 仍然只是唤醒信号；它不保存消息正文，也不向前端暴露为队列。`Session.queue_pending` 继续作为跨重启的持久化真源。该边界与现有 at-most-once 设计保持一致。

## 3. 统一队列项模型

### 3.1 推荐字段

统一队列项建议采用 envelope 形式：

```json
{
  "id": "q_01J...",
  "schemaVersion": 2,
  "source": "user",
  "kind": "task",
  "text": "请检查这个项目",
  "payload": null,
  "position": 30,
  "createdAt": "2026-09-01T12:00:00Z",
  "updatedAt": "2026-09-01T12:00:00Z",
  "dispatchState": "queued",
  "revision": 1,
  "clientMessageId": "browser-uuid",
  "taskId": null,
  "sourceSessionId": null
}
```

字段含义：

| 字段 | 说明 |
|---|---|
| `id` | 队列项永久身份。前端、服务端、Worker 和 history 都引用它 |
| `source` | 来源及权限标签，由服务端生成，不能信任客户端传值 |
| `kind` | 消息处理语义，例如 `task`、`report`、`qq` |
| `text` | 面板展示文本；用户 task 直接使用 |
| `payload` | report、QQ 等来源的结构化原始数据 |
| `position` | 所有来源共享的队列顺序 |
| `dispatchState` | 当前投递/执行状态 |
| `revision` | 防止编辑和排序请求覆盖较新的数据 |
| `clientMessageId` | 浏览器断线重试的幂等键 |
| `taskId` | Agent 编排任务的幂等键 |
| `sourceSessionId` | report 或 Agent 消息的来源 Session |

### 3.2 `source` 和 `kind` 必须分开

不要用一个字段同时表达来源和处理类型。推荐使用以下组合：

| source | kind | 示例 |
|---|---|---|
| `user` | `task` | 用户在聊天输入框发送的消息 |
| `agent` | `task` | Meta Agent 或其他 Agent 派发的任务 |
| `report` | `report` | 被管理 Session 的完成报告 |
| `qq` | `qq` | QQ inbox 提醒 |
| `system` | `task` | 系统提示或恢复指令 |

这样 UI 可以分别显示“来源标签”和“消息类型”，Worker 也不需要通过缺失字段猜测消息类型。

### 3.3 ID 规则

所有新队列项都必须在服务端生成原生 ID，例如 `q_` 加随机 UUID。

不再把 report 或 QQ 内容 hash 作为正式身份。内容 hash 可以暂时用于迁移旧数据或兼容旧客户端，但不能继续作为新消息 ID，因为：

- 两条内容完全相同的 report 必须是两条不同的队列项。
- 内容变化后 hash 会变化，旧 UI 操作可能找不到原条目。
- 同一个 report 不能仅凭内容判断是否已经消费。

## 4. 来源写入规则和权限

### 4.1 服务端决定来源

客户端调用用户入队 API 时只能提交文本和幂等键：

```json
{
  "text": "请检查这个项目",
  "clientMessageId": "browser-uuid"
}
```

服务端强制写入：

```json
{
  "source": "user",
  "kind": "task"
}
```

客户端不能通过请求体把自己的消息伪装成 `report`、`qq` 或 `system`。

同理：

- report 订阅链路固定写入 `source=report`。
- QQ inbox 链路固定写入 `source=qq`。
- `agent_assign` / `agent_send` 固定写入 `source=agent`。
- 系统恢复、system prompt 等内部投递固定写入 `source=system`。

### 4.2 编辑权限

只有满足以下条件时允许编辑正文：

```text
item.source == "user"
item.dispatchState == "queued"
```

编辑只修改 `text` 和 `revision`，不改变 `id`、`createdAt`、来源和幂等身份。

以下情况拒绝编辑，并返回结构化错误：

```json
{
  "ok": false,
  "error": {
    "code": "queue_item_not_editable",
    "message": "Only queued user messages can be edited"
  }
}
```

report、QQ、Agent 和 system 项返回：

```json
{
  "ok": false,
  "error": {
    "code": "queue_item_readonly",
    "message": "Only user-originated queue items can be edited"
  }
}
```

### 4.3 排序权限

所有来源都允许调整顺序，但只针对尚未被 Worker 接管的队列项。

`in_flight`、`uncertain` 项不能被移动。否则用户看到的顺序和 Worker 实际已经接受的顺序会产生无法解释的差异。

### 4.4 删除权限

所有来源都允许删除 `queued` 项。

对于已经进入 `in_flight` 的项，不直接从持久队列删除：

- 如果 adapter 支持可靠取消，转为 `cancel_requested`。
- 如果无法可靠取消，返回“已执行中，不能删除”。
- `uncertain` 项默认不自动重试，也不允许通过普通删除隐藏其不确定状态。

这样可以避免“界面显示删除成功，但 Provider 仍执行了这条消息”的状态欺骗。

## 5. 队列状态机和 Worker 消费

### 5.1 状态机

```text
queued
  ├─ Worker claim → in_flight
  │                    ├─ 成功 → completed → history 记录后移除
  │                    ├─ 可确认失败 → failed
  │                    └─ Worker/Provider 崩溃 → uncertain
  └─ 用户删除 → deleted → 移除
```

状态语义：

| 状态 | 是否显示 | 是否编辑 | 是否排序 | 是否删除 |
|---|---:|---:|---:|---:|
| `queued` | 是 | 仅 user | 是 | 是 |
| `in_flight` | 是，显示执行中 | 否 | 否 | 仅取消能力可靠时允许 |
| `uncertain` | 是，显示需处理 | 否 | 否 | 默认否 |
| `cancel_requested` | 是，显示取消中 | 否 | 否 | 否 |
| `failed` | 可选，建议保留失败记录 | 否 | 否 | 按失败策略处理 |

### 5.2 Claim 不能再立即丢失身份

当前 Worker claim task 时会从 `queue_pending` 移除 item。统一队列需要改为：

1. 在持久队列中找到 `position` 最小的可执行项。
2. 原子写入 `dispatchState=in_flight`、`claimedBy`、`claimedAt`、`leaseId`。
3. 执行期间队列 API 仍能返回该 item。
4. 成功写入 history，并确认完成后再将 item 标记完成并移除。

`leaseId` 用于防止旧 Worker 在重启后误更新新一代 Worker 的队列项。租约超时不能直接重放，因为 Provider 可能已经收到消息；应先进入 `uncertain`，遵守现有 at-most-once 取舍。

### 5.3 统一调度器

如果 task、report、QQ 仍由彼此独立的消费者读取，那么前端虽然显示一列，实际执行顺序仍然可能不一致。

因此需要一个统一调度入口：

```text
读取 queue_pending
  → 找 position 最小且 dispatchState=queued 的 item
  → 写入 in_flight lease
  → 按 kind 调对应处理器
       task   → Provider
       report → Agent 报告注入
       qq     → QQ 消息注入
  → 成功写 history / receipt
  → 完成消费该 queueItemId
```

第一版建议不合并不同 item 的正文，每个 item 单独进入消费边界。后续如果需要降低报告注入次数，只允许将连续的 report 项批量处理，不能跨越中间的 user 或 qq 项。

## 6. API 设计

### 6.1 入队

```http
POST /api/sessions/{session_id}/queue
```

用户请求：

```json
{
  "text": "请检查这个项目",
  "clientMessageId": "browser-uuid"
}
```

返回：

```json
{
  "ok": true,
  "item": {
    "id": "q_xxx",
    "source": "user",
    "kind": "task",
    "text": "请检查这个项目",
    "position": 30,
    "dispatchState": "queued",
    "revision": 1
  },
  "queueRevision": 42
}
```

`/api/send` 和 WebSocket `user_inject` 可以保留为兼容入口，但内部必须转为同一个服务端 enqueue 函数。`accepted` 的含义改为“已持久化入队”，不能仅表示 WebSocket 已写入内存信号队列。

### 6.2 查询

```http
GET /api/sessions/{session_id}/queue
```

返回完整统一列表：

```json
{
  "items": [],
  "queueRevision": 42
}
```

前端必须按服务端返回顺序展示，不再把 local queue 和 Agent queue 拼接。

### 6.3 编辑

```http
PATCH /api/sessions/{session_id}/queue/{item_id}
```

```json
{
  "text": "修改后的内容",
  "expectedRevision": 1
}
```

服务端校验来源、状态和 revision。revision 冲突返回 `409` 或统一的 `queue_revision_conflict` 错误，并附带最新队列快照。

### 6.4 排序

```http
PATCH /api/sessions/{session_id}/queue/order
```

```json
{
  "orderedIds": ["q_report", "q_user", "q_qq"],
  "expectedQueueRevision": 42
}
```

排序接口必须覆盖所有来源，不能只重排 task 而让 report/QQ 保持原槽位。

服务端应原子校验：

- 请求中的 ID 属于当前 Session。
- 不包含已被 claim 的 item，或仅允许它们保持原位置。
- 没有重复 ID。
- 未列出的合法 queued 项按既定规则追加，而不是静默丢失。
- `expectedQueueRevision` 未过期。

### 6.5 删除

```http
DELETE /api/sessions/{session_id}/queue/{item_id}
```

删除返回被删除的 `queueItemId` 和新的 `queueRevision`，便于前端只删除同一身份的缓存项。

## 7. WebSocket 事件

建议增加以下增量事件：

```text
queue.item_added
queue.item_updated
queue.item_removed
queue.snapshot
```

事件正文必须带：

```json
{
  "sessionId": "ses_xxx",
  "queueRevision": 42,
  "item": {}
}
```

事件只用于降低刷新延迟，服务端快照仍是事实来源。断线重连时前端必须重新调用 GET queue，并以较新的 `queueRevision` 覆盖本地镜像。

## 8. 前端改造

### 8.1 Store

逐步废弃：

- `queueStore.queues`
- `pan.sendQueue.<sessionId>`
- 本地 `flush()` 发送调度
- 发送成功后从 local queue 删除的 ack 逻辑

保留并统一为：

```text
sessionQueues[sessionId]
loadSessionQueue()
enqueueUserMessage()
updateQueueItem()
reorderQueueItems()
deleteQueueItem()
```

Store 可以保留短期内存缓存和乐观渲染，但缓存不是队列，不应在服务器未确认前显示为“已入队”。

### 8.2 输入框发送

发送逻辑改为：

1. 校验文本。
2. 请求服务端 enqueue。
3. 服务端持久化成功后清空输入框并显示队列项。
4. 服务端失败时保留输入框文本，提示“消息尚未入队”。

网络不可用时不能显示“待发送”状态，因为此时没有真实服务端队列项。可以保留输入框草稿，但草稿不属于本设计的队列。

### 8.3 队列面板

面板只显示一组服务端队列：

```text
服务端队列 4

[用户]   请检查这个项目       编辑 上移 下移 删除
[report] 子 Agent 已完成       上移 下移 删除
[qq]     收到 QQ 消息          上移 下移 删除
[用户]   再检查测试            编辑 上移 下移 删除
```

控件规则：

- `user + queued`：编辑、排序、删除。
- 其他 `queued`：排序、删除。
- `in_flight`：显示“执行中”，所有修改按钮禁用。
- `uncertain`：显示风险状态，不自动重发。
- 所有操作以 `queueItemId` 为 key，不使用数组 index 作为长期身份。

原有“批量发送”如果保留，应变成入队前的文本组合操作。不能先把多条消息写入本地队列，再由前端逐条发送。

## 9. 数据迁移

### 9.1 服务端旧 queue_pending

启动恢复或首次读取时为旧项补齐 envelope 字段：

- task：保留已有 task UUID；没有 UUID 时生成新的原生 ID。
- report/QQ：生成一次性原生 ID并持久化，不能继续每次按内容 hash 临时生成。
- 推断并固定 `source` 和 `kind`。
- 按原列表顺序生成 `position`。
- 没有明确状态的项默认 `queued`，但对旧 `in_flight` 项按现有 at-most-once 规则进入迁移处理。

迁移必须是幂等的，重复启动不能生成第二个队列项。

### 9.2 前端 localStorage 旧队列

不能在升级后自动重发旧 localStorage 内容，否则可能产生重复执行。

首次升级发现旧数据时显示一次迁移提示：

```text
发现 3 条旧版本地待发送消息
[全部入队] [逐条查看] [暂不处理]
```

用户确认后，将旧本地 ID 作为 `clientMessageId` 导入服务端。服务端按幂等键判断是否已经导入。迁移成功后删除对应的 `pan.sendQueue.<sessionId>`。

如果用户选择暂不处理，旧内容只能作为草稿保留，不能混入新的服务端队列展示。

## 10. 分阶段实施

### 阶段 A：只增加统一数据契约

- 增加原生 queue item ID。
- 为 task/report/QQ 增加 `source`、`kind`、`position`、`dispatchState`。
- 增加旧数据一次性迁移。
- 暂不改变用户发送路径。

验收：旧功能不变；相同内容的多条 report/QQ 可以独立操作。

### 阶段 B：统一服务端 enqueue 入口

- 新增内部 `enqueue_queue_item()`。
- 用户、Agent、report、QQ 全部使用同一入口。
- `clientMessageId` 和 `taskId` 继续走持久化幂等检查。
- HTTP 和 WebSocket 入口统一返回 queue item ID。

验收：服务端日志和 queue API 能看到所有新来源项，且重复请求不会创建第二项。

### 阶段 C：Worker lease 和统一调度

- claim 改为持久化 `in_flight` lease。
- 统一 task/report/QQ 的调度顺序。
- 增加 crash、restart、取消和 uncertain 处理。
- history 与 queue item 使用相同 ID 关联。

验收：Worker 重启不会重复执行；服务端队列顺序等于实际消费顺序。

### 阶段 D：前端切换

- 输入框直接请求服务端 enqueue。
- 面板删除 local queue，只展示服务端快照。
- 增加 user 项编辑。
- 所有来源支持 queued 状态下的排序和删除。
- 增加 WebSocket 增量事件和重连快照。

验收：前端刷新、多开页面和 Worker 忙闲变化下，队列项仍然是同一个 ID。

### 阶段 E：迁移和清理

- 提供旧 localStorage 队列的显式导入。
- 观察一段时间重复发送、顺序错乱和队列恢复指标。
- 删除旧 `flush()` 和 localStorage 发送队列逻辑。
- 更新 Pan skill 和 HTTP/MCP 文档。

## 11. 必须覆盖的测试

### 服务端

- 用户消息持久化成功后才返回 accepted。
- 相同 `clientMessageId` 重试不重复入队。
- 相同 `taskId` 重试不重复入队。
- report/QQ 内容相同时仍有不同原生 ID。
- 非 user 项编辑返回 `queue_item_readonly`。
- 已 claim 项编辑被拒绝。
- 全来源排序后持久顺序正确。
- 并发排序遇到 revision 冲突不会覆盖新顺序。
- queued 项删除不会被 Worker claim。
- Worker claim 与删除并发时不会出现幽灵执行。
- Worker 在 Provider 写入前后崩溃分别进入正确状态。
- 重启恢复不会自动重复执行 uncertain 项。
- 旧 localStorage 导入重复调用不会重复入队。

### 前端

- 发送成功前不清空输入框。
- 服务端确认后列表出现同一个 `queueItemId`。
- WebSocket ack 丢失后重连不会出现重复卡片。
- 用户项显示编辑按钮，report/QQ 不显示编辑按钮。
- 所有 queued 来源可以排序和删除。
- in-flight 项按钮正确禁用。
- 队列刷新不会把已删除或已消费项重新显示。
- 多窗口收到较旧快照时不会覆盖新快照。

### 实际恢复测试

- Worker 执行中被 kill。
- Pan 服务重启。
- 浏览器 WebSocket 在入队确认前断开。
- 服务端写入成功但确认消息丢失。
- 两个页面同时编辑、排序和删除同一 Session 队列。

## 12. 风险和取舍

风险等级：中高。

主要风险不在 UI，而在 Worker 消费边界：

1. claim 从“立即移除”改为“持久化 in-flight”后，必须处理租约、恢复和不确定执行。
2. report、QQ、task 当前有不同消费路径，必须先统一调度，否则只能做到“显示顺序统一”，做不到“真实执行顺序统一”。
3. 删除和执行可能同时发生，必须以服务端状态为准，不能只做前端乐观删除。
4. 编辑后的消息要保留同一 queue item ID，同时用 revision 防止旧请求覆盖新内容。
5. 旧 localStorage 消息不能静默迁移，否则会引入重复执行。

推荐的取舍是继续采用 at-most-once：发生 Provider 已接收但 Pan 未确认的情况时进入 `uncertain`，不自动重放；由用户明确决定后续处理。该取舍牺牲极端故障下的自动完成率，换取不重复执行的重要安全性。

## 13. 暂不纳入第一版的内容

- 跨 Session 的全局队列排序。
- 已经 `in_flight` 项的强制撤回。
- 自动重放 `uncertain` 项。
- 不同来源消息的正文自动合并。
- 将已完成 history 无限期留在 pending queue 中。
- 通过浏览器离线缓存伪造“已入队”。

第一版完成的定义是：所有新消息都具有服务端原生身份，前端只展示服务端队列，来源权限正确，排序/编辑/删除不会造成重复执行或幽灵执行。
