# CLIConductor 重构方案评估（by k3）

> 基于 `docs/plans&overviews/目标与范围.md`、`跨平台适配计划.md` 及 Maestro 对比分析。

---

## 一、产品设计角度

### 1. 做得好的地方

- 边界表（做/不做）非常克制，尤其是"不自己实现 AI Agent"、"不管理 Worker 工作目录"，避免了大范围蔓延。
- Maestro 对比分析的结论清醒：不与桌面 IDE 正面竞争，而是强化 multi-channel 服务化差异。
- "通道是插件"的心智模型清晰，扩展路径对潜在用户和贡献者都友好。

### 2. 核心建议

**（1）补齐用户画像与"第一杀手场景"**

当前 P0 同时塞入 Dashboard、Meta-Agent、QQ Bot 三件事，等于三个产品并行。方案需要回答"谁在用"以及"他们第一次离不开这个功能的原因是什么"。建议把 P0 收敛到一条最短闭环：

> 我在外面，用 QQ 发一句话，家里的 Worker 开始干活，做完把结果推回我手机。

所有 P0 工作围绕这条链路，其余功能降级。

**（2）权限/多用户模型是过早设计**

"最高权限用户拥有一切数据可视权、受限通道不可 spawn"这套 RBAC 对单用户个人工具是负担。既然"多用户暂不"，P0 只保留二元模型即可："我" vs "外人"（QQ 来源辨析）。细粒度权限等真出现第二个用户再设计。

**（3）Memory 模块是范围蔓延高危区**

边界写"不做通用知识库"，但 Memory 职责里又包含"跨 Session 知识沉淀 + 用户偏好记忆"，这两者就是知识库。建议第一版 Memory 只做**检索**（摘要/标签/搜索），这是多 Session 场景的刚需。知识沉淀与偏好记忆砍掉或推迟到 P2 之后。

另外，摘要依赖 LLM 调用，有持续成本。产品上需要保留"关闭自动摘要"的选项。

**（4）Meta-Agent 建议从 P0 降到 P1**

Meta-Agent 是"用 Agent 管 Agent"，是放大器不是地基。如果 Dashboard 里手动管多个 Worker 的场景还没跑顺，自动调度只是在不稳定底座上加复杂度。建议顺序：

1. 人工多 Worker 管理做到流畅；
2. 收集真实调度模式；
3. 再让 Meta-Agent 自动化这些模式。

**（5）每个 Phase 都需要一个用户可感知的交付**

Phase 1"清洁 Core"是纯内部工作，用户价值为零，容易烂尾。建议把"跨平台适配"或某个小功能（如 Session 搜索）捆进 Phase 1，保证每个阶段有可演示的成果。

### 3. 值得再考量的点

- **安全应单列 P0 设计项。** "远程暴露 + QQ 接收消息 + 能执行命令"风险极高。方案里来源辨析只有一行，建议明确：默认仅监听 localhost、QQ 白名单、危险操作二次确认。
- **移动端是远程主战场。** Dashboard 是否 mobile-first 会影响前端选型，这应该在"纯 TS vs 框架"讨论前先确定。
- **缺少"通知"闭环。** 远程场景的核心是"任务完成/出错时叫我"。QQ 通道天然可做推送，Dashboard 侧可考虑 Web Push，建议进 P0。
- **QQ 通道的外部依赖风险。** NapCat 是非官方协议，有封号/协议变更风险。架构上已能做到通道隔离，建议把"QQ 通道失效时 Core 与 Dashboard 完全不受影响"写进验收标准。
- **异常状态 UX 应提前。** "Worker 状态机补全（spawning/zombie/queued）"放在待讨论，但 Worker 挂了用户能否一眼看到、一键重启，是高频痛点，建议挪入 Phase 1。
- **成本可见性。** 多 Worker 并发烧钱快，Memory 做摘要时顺手记录 token 用量并在 Dashboard 展示，投入小、用户感知强。
- **模块数量对个人项目偏多。** Core/Memory/Adapters/Web/QQ/Remote/SDK 七个模块，"独立部署"的收益在单人开发期抵不过联调成本。建议物理上先保持单进程 + 目录隔离，"独立部署"作为架构允许的能力而非必须执行的动作。

## 二、代码框架角度

### 1. 总体判断

模块拆分方向（Core 最小化、通道插件化、Adapter 协议化）是对的，目录边界也清晰。但方案在**通信方式**上犯了"把微服务思维搬进单体项目"的典型错误，并且把两个本应前置的架构决策错误地推迟了。

### 2. 关键问题

**（1）"模块间只走 HTTP/WS"是过度设计，应改为"接口隔离 + 同进程通信"**

这条原则会让每个模块白捡分布式复杂度：序列化开销、连接管理、重连、丢消息、启动顺序依赖、跨进程调试。最典型的例子是 Memory——"监听 Core WS 事件流"意味着 Memory 要维护 WebSocket 客户端、处理断线重连和事件空洞，而它明明与 Core 在同一台机器上。

建议改为两层：

- **进程内**：定义 Python 抽象接口（Core 门面 + 事件订阅 API），模块间通过接口调用，零序列化成本，保留类型检查。
- **进程间**：HTTP/WS 只作为**对外协议**（给远端通道、SDK、第三方用），是门面之上的薄层。

"独立开发、独立测试"靠目录边界 + 接口约束即可实现。等某个模块真需要独立部署时，它再走对外协议——架构上始终保留这个选项，不必现在为所有模块支付成本。

**（2）Adapter 同进程 vs 独立客户端不是待讨论项，是 Phase 1 前置决策**

这条被列在"待后续阶段讨论"最后一项，但它决定整个进程模型。Adapter 要解析 CLI 的 stdout/PTY 流，是有状态的长连接。如果 adapter 是独立进程，每个 Worker 就变成「CLI 进程 + adapter 进程 + Core」三方转发，进程数翻倍、输出流跨进程搬运、延迟和故障点都增加。

结论几乎必然是 **adapter 必须同进程**，作为 Core 内部的插件库。建议直接写死这个决策。

**（3）事件协议版本化不能推迟到模块设计阶段——它就是 Phase 1 交付物**

Phase 1 的关键交付是"稳定的 Core API 契约"，但事件 schema 被推迟了。没有事件 schema，契约就是空壳。而这套系统本质上是事件驱动的（Worker 输出流、状态变化），REST 端点只是控制面。Phase 1 应该先定义：

- 事件类型清单 + Pydantic 模型（如 `worker.output`、`worker.status`、`session.updated`）；
- WS 订阅/过滤语义（通道收全部事件还是按 session 订阅？）；
- 版本字段。

顺带一个内部矛盾：既然"不许 import 彼此"，各模块怎么共享事件模型？正确做法是抽一个**独立的 protocol 包**（只有数据模型，无逻辑），允许所有人 import——这不违反"不 import 内部实现"的原则。

**（4）事件流需要持久化/重放机制，否则 Memory 数据一致性无解**

Core 存原始 history，Memory 靠监听事件流建索引。那 Memory 重启、崩溃或晚于 Core 启动时，漏掉的事件怎么办？摘要会无声地缺斤短两。

轻量解法：Core 把事件写 append-only log（哪怕只是 SQLite 表），消费者记录 offset，重连后从 offset 续传。这是事件溯源的最低配，改动小但消除了整类一致性问题。

### 3. 次要但值得记录

- **Meta-Agent 的"视图"和普通通道不同。** LLM 消费不了原始输出流（context 会爆），它需要的是过滤/摘要后的事件。`/ws/agent` 不能只和普通 WS 差一个路径，协议层面要考虑"agent 视图"——这又回到事件订阅语义要先定义。
- **Core 重启后 Worker 孤儿进程怎么办？** 当前实现就存在这个问题，重构方案没提。对"Core 作为长期服务"的目标，"Core 重启后 re-attach 或回收存量 Worker"是核心可靠性场景，应进 Phase 1。
- **迁移路径低估了 Phase 1 工作量。** 当前 `packages/web/server.py` 近千行直接 import Core 内部，"外部只走 HTTP/WS"意味着 Phase 1 就要重写整个 Web 层通信。按上述第 1 条修正后工作量骤减：Phase 1 只需把 Core 收敛出门面接口，Web 层改为调门面（进程内），对外协议薄层后置。
- **前端框架选型是 Phase 2 阻塞项。** `app.ts` 已 1500+ 行手写 DOM，抽离 WebChannel 之前不定选型等于白拆一次。
- **缺契约测试方案。** "模块独立测试"只提了原则，没有机制。protocol 包 + 每个模块对契约的测试用例是最低成本的做法。

---

## 三、一句话总结

**分层方向对，但把"逻辑隔离"误实现成了"网络隔离"，会把单人项目拖进分布式复杂度。修正为接口隔离 + 同进程通信 + 对外协议薄层，并把 adapter 同进程、事件 schema、事件重放三个决策提前到 Phase 1，框架就站得住。**

by k3
