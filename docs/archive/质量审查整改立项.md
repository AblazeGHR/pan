## 二、需决策后再修（修法有取舍 / 涟漪）

### 2.1 安全（鉴权推迟后的实际边界）

#### D1. workdir 放行策略（质检 #2）

- **现状**：`_ALLOWED_WORKDIR_ROOTS=None`，`_resolve_workdir` 对绝对路径直接 `mkdir` 返回，结合 `/api/fs/*` 可对磁盘任意目录读写删。
- **约束**：cbc/kimi import 流程的 workdir 就是绝对路径（真实项目目录），直接收紧到 `WORKDIRS_DIR` 会打断 import/接管。
- **选项**：
  - A. 白名单根目录列表（`_ALLOWED_WORKDIR_ROOTS` 配置化，import 放行、spawn 拒绝）
  - B. 「绝对路径 workdir 只读，写入仅限 `WORKDIRS_DIR`」
  - C. 维持现状 + 依赖 loopback 绑定（不推荐，见下）
- **与鉴权的关系**：鉴权已决定推迟（见 D0），因此 workdir 放行是当前**唯一**的实际安全边界，优先级高于其它所有项。
- **待决策**：选 A / B / C。

#### D0. 鉴权（状态记录，已决定推迟）

用户已两次确认推迟（`main.py:23-35` 注释 + 2026-08-13）。姿态 = 绑 127.0.0.1 + 非回环告警；未来暴露公网再上 shared-secret。**不再反复催修，安全讨论聚焦 D1/D2。**

#### D2. manifest 信任模型（质检 #16）

- **现状**：`_parse_mcp_server` 不校验 `command/args/env/cwd`，manifest 可声明任意可执行文件（如 `cmd /c ...`），随后被 cbc 子进程执行。
- **关键问题**：manifest 是本地用户配置（`config.json` 的 `plugin_manifests`）还是可能来自第三方插件？信任级别决定校验强度。
- **选项**：A. 视为受信（本地配置），本条降级为「记录在案」；B. 视为不可信，像 `memory_dir` 一样做容纳校验（`relative_to(plugin_dir)`）+ command 白名单。
- **待决策**：A / B。

### 2.2 架构

#### D3. server.py 拆分形态（质检 #22）

- **现状**：1911 行 God object，40+ 路由横跨 8 领域，cbc/kimi import、rename、branch 逻辑成对复制。
- **选项**：A. 按领域拆 Router（sessions/workers/fs/characters/memory/import）；B. 只抽公共 helper 不动路由；C. 引入 service 层。
- **约束**：须与「通道模块只走 HTTP/WS、不 import core 内部」的约定协调。
- **待决策**：拆到 A 还是先 B；拆分与当前 P0（QQ 路由）等任务的先后。

#### D4. legacy `app.ts` 去留（质检 #30）

- **现状**：2195 行 God file，`/` 是「稳定备份」入口，React 已主力。
- **选项**：A. 冻结（只修 bug，不投架构）；B. 继续小修；C. 明确退役时间。
- **倾向**：A（冻结）。
- **待决策**：A / B / C。

#### D5. enrich 协议 sync→async（质检 #11）

- **现状**：`enrich_after_result`（`cbc/adapter.py:302`）→ `_read_jsonl_new_entries`（`:337`）含 `time.sleep(0.2)`，在异步 `_read_stdout`（`worker.py:187`）里同步调用，阻塞事件循环 0.2s/次。
- **修复涟漪**：`enrich_after_result` 是 `CliAdapter` Protocol 的**同步**方法，改 `await asyncio.sleep` 需把该方法改 async，波及 Protocol 定义 + cbc/kimi 两实现 + `worker.py` 调用点。
- **选项**：A. Protocol 改 async（彻底但波及广）；B. sleep 移出（在 worker 侧 await sleep 后调 sync enrich）；C. 容忍（0.2s/次，仅 result 事件触发，频率低）。
- **待决策**：A / B / C。

#### D6. kimi fork 判定重构（质检 #4）

- **现状**：`KimiAdapter.supports_fork=True`（`kimi/adapter.py:96`），但 `fork_args` 完成文件复制后返回 `[]`（`:167`）；`branch_worker` 用 `not supports_fork or not extra_args`（`worker.py:831`）判「不支持 fork」，导致 kimi 分支永远失败且残留孤儿目录。
- **修复涟漪**：若让 `fork_args` 返回非空标记，`build_spawn_args` 的 `args.extend(extra_args)` 会把标记塞进进程参数。
- **选项**：A. `branch_worker` 去掉 `or not extra_args`，只依赖 `supports_fork`；B. `fork_args` 返回空但分支流程改走「fork 后 spawn 不带 fork 参数」路径。
- **待决策**：A / B。

### 2.3 并发 / 持久化

#### D7. Session 原子写 + 缓存锁（质检 #9）

- **现状**：`_save_sync`（`session.py:191-197`）用 `write_text` 非原子；`save_async` 走 `asyncio.to_thread`，与事件循环并发写同一文件；`_cache` 跨线程无锁。
- **修复方式**：临时文件 + `os.replace` 原子写 + `_cache` 加 `threading.Lock`。
- **注意**：触及高频率热路径（每条 stdout 事件都 `save_async`），且 `save_async` 的线程模型需确认锁的作用域不引入死锁。
- **待决策**：锁粒度（全局一把 vs 每 session 一把）；原子写是否需保留 `indent=2` 的人类可读格式（`os.replace` 无影响，但需确认 to_dict 稳定性）。

#### D8. 广播并发发送（质检 #8）

- **现状**：`broadcast`（`server.py:108-122`）对同一 WebSocket 无锁并发 `send_json`，多 worker 同时广播时 Starlette ws 非并发安全。
- **严重度**：真实但可能罕见（需并发广播 + 底层背压同时发生）。
- **选项**：A. 每连接 `asyncio.Lock`（需锁表 + 断线清理）；B. 串行化发送队列；C. 接受并 log。
- **待决策**：A / B / C。

#### D9. QQ 同会话并发消息串线（质检 #14）

- **现状**：`_pending[session_id]` 被后到消息覆盖（`plugin.py:320-321`），同 session 两条并发消息设同一 event，响应串线（后到的拿到先到的答案）。
- **修复方式**：每 session 串行化（`asyncio.Lock` 或消息队列），或改轮询为「按 message_id 匹配」。
- **待决策**：串行化粒度；是否与 P5（轮询改 WS 推流）合并处理。

### 2.4 性能（含隐藏取舍）

#### D10. `load_config()` 缓存 vs 热重载（质检 #10）

- **现状**：`_cbc_config`（`cbc/adapter.py:62-65`）每次属性访问都 `load_config()` 读盘解析，热点路径反复 IO。
- **隐藏取舍**：当前实现**每次重读**，意味着运行时编辑 `config.json` 会被立刻生效（隐式热重载）。直接加缓存会破坏这一行为。
- **选项**：A. 加缓存 + 接受失去热重载；B. 加缓存 + 文件 mtime 失效检查；C. 维持现状。
- **待决策**：A / B / C。

#### D11. embedding 存储 ANN 升级（质检 #13）

- **触发条件型**：memory 审查已定「单 character >~1 万 chunk 才动」。当前数据量小，**不现在决策**，仅在数据量爆发时再立项。

#### D12. API key 落库改 hash 的缓存失效（质检 #7）

- **现状**：`embedder.py:481-482` 用 `api_key[-8:]` 作 `provider_key` 持久化。
- **修复方式**：改 `sha256(api_key)` 摘要。
- **代价**：旧 `embedding_cache` 表的 `provider_key` 全失效 → 缓存 miss → 重 embed 一次（一次性成本）。
- **待决策**：是否接受一次性缓存失效；是否需要迁移旧 key。
