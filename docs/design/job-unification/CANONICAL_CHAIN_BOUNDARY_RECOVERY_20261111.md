# Canonical chain boundary recovery

A cold host may continue an original running Run only when its durable aggregate proves a contiguous completed prefix followed by steps with no Attempt. Every completed step must have exactly one succeeded Attempt and one succeeded effect with the complete original key, original execution fence, and matching persisted output. There must be no unresolved effect admission, pending external Attempt, or cancellation. The original operation must be an admission operation (`create`, `run-again`, or `clone-and-run`) whose receipt binds the same Run, admission and Job. The existing owner/writer transaction and dispatch guards remain authoritative.

New canonical effect records optionally carry `attempt`, the original execution snapshot supplied at receipt commit. This is an additive field on the existing effect wrapper; the provider receipt is unchanged. The snapshot is checked using `independent_executor.fence` against the original Attempt before writing. Recovery compares the snapshot using that same function and the complete key using `Ledger.effect_key`. The generated strict effect schema validates the snapshot, including its lease. Old effects without a snapshot remain readable but do not authorize continuation. Recovery never backfills identity or queries a provider to infer it.

A proven boundary transitions the same Run to `retry_wait`; the original dispatcher skips completed steps and applies current authority and original frozen-definition checks before starting the next step. Missing or conflicting proof preserves `uncertain`, with no next-step call. A running/unknown Attempt is never authorized by this boundary rule.

Evidence lives under `.tmp/canonical-ci-final/`: `chain-boundary-crash-red.xml` reproduces the original subprocess-crash failure; `boundary-fence-r1.xml` covers real `os._exit(23)` after the first committed receipt, plus missing/mismatched fence, key, output, operation, admission and Job negatives. `effect-fence-regression.xml` covers the write-fence rollback, generated schemas, HTTP and migrated chain contracts. These are isolated local tests, not remote CI or UI acceptance.
