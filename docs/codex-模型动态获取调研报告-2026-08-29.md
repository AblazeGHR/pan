# Codex 模型动态获取调研报告

- 日期：2026-08-29
- 分支：`feature/codex-models`（worktree：`D:/project/pan-codex-models`）
- 类型：调研报告 + 第一阶段实现记录
- 关联代码：`packages/core/adapters/codex/adapter.py`

## 背景（调研前）

调研开始时，Pan 的 codex adapter（`packages/core/adapters/codex/adapter.py`）的
`supported_models` 三级回退为：

1. `config.json` → `codex.models` 白名单（当前为空）
2. `~/.codex/config.toml` 的 `model_catalog_json`（cc-switch 生成的模型目录文件，当前为 None）
3. 兜底 `default_model` 单元素列表

**当时的实际效果：模型列表只有默认单模型。** 目标是找到从 Codex 本身**动态获取**可用模型的办法，
不靠手动维护白名单。

## 结论速览

**可行，且已找到官方动态源。** 两条路径：

1. **首选（零额外成本）：读 `~/.codex/models_cache.json`** —— codex CLI 自身维护的动态模型缓存（登录官方账号时自动从后端拉取，含 `fetched_at`/`etag`）。实测确认其内容随 codex 运行实时刷新，且**每个模型自带 reasoning effort 列表**（`default_reasoning_level` + `supported_reasoning_levels[].effort`），一次解析可同时拿到模型列表与 effort 映射。
2. **备选（强制刷新）：spawn `codex debug models`** —— 隐藏调试命令，直接输出完整模型目录 JSON，每次调用触发远程刷新。成本：输出 ~300KB（含大段 system prompt）、需登录态、子进程开销。

## 探索路径与结果

### 1. codex CLI 内建

| 尝试 | 结果 |
|---|---|
| `codex --help` | 顶层**无** models 子命令（有 login/logout/doctor/debug/features 等） |
| `codex exec --help` | 只有 `-m/--model`（指定模型），**无** `--models` 列举选项 |
| `codex models` | 不存在 |
| **`codex debug models`** | **命中**。help 描述 "Render the raw model catalog as JSON"。实测输出完整目录，8 个模型 |
| `codex debug models --bundled` | 输出**内置**目录：含旧模型 `gpt-5.2`、**无** `gpt-reserve`。与默认输出不同 → 证明默认输出是**动态刷新**源，非内置硬编码 |

关键验证：`codex debug models` 运行前后 `~/.codex/models_cache.json` 的 mtime 与 `fetched_at` 一致更新（08-29 10:50 本地），**确认该命令触发远程拉取并落盘缓存**。

### 2. codex 包/安装目录

- 包：`@openai/codex@0.149.1`，实际是 Rust 二进制 `codex.exe`（`node_modules/@openai/codex-win32-x64/vendor/.../bin/codex.exe`）。
- 二进制内确认存在 `models_cache.json`、`models.json`、`model_catalog_json` 及错误串 "failed to load models cache"、"failed to parse model_catalog_json path"。
- **`~/.codex/models_cache.json`（198KB）** —— 关键发现。结构：`{"fetched_at", "etag", "client_version", "models":[{slug, display_name, visibility, supported_in_api, priority, context_window, default_reasoning_level, supported_reasoning_levels, ...}]}`。当前 8 个官方模型，slug 与 `debug models` 输出**完全一致**。
- `~/.codex/models.json`（114KB，08-26 22:30）—— 3 个 deepseek 自定义模型（deepseek-v4-flash/pro/flash-vision-exp），与官方目录无关，不是动态源。

### 3. 配置侧动态源

- `~/.codex/config.toml` 当前**无** `model_catalog_json` 字段（全文 231B 确认），故 Pan 现有 `_parse_models_from_catalog()` 读到 None。
- cc-switch 已装（`/d/software/cc-switch/cc-switch.exe`，GUI），数据在 `~/.cc-switch/cc-switch.db`。库中 3 个 codex provider：**OpenAI Official（当前）**、Zhipu GLM、SiliconFlow。切到第三方时 cc-switch 会写 `model_catalog_json = "cc-switch-model-catalog.json"` 到 config.toml 并生成该文件（当前文件是 GLM 的 2 个模型）。→ cc-switch 是**手动切换**机制，非自动动态源，且官方 provider 下不生效。

### 4. 官方 API

- 二进制内只有 `chatgpt.com/backend-api/...` 端点字符串，**无明确 /models 路径**；未实际调用需认证接口。
- 间接证据：`models_cache.json` 的 `fetched_at`/`etag` 即后端拉取产物，**说明后端确实有模型目录接口**，只是 codex 未公开其路径（调用链走 `chatgpt.com/backend-api`）。

### 5. 官方文档/检索

- 官方 models 文档（developers.openai.ac.cn/codex/models）只列推荐模型 + `-m` 用法，**未文档化**列举命令；确认模型可用性依赖登录态（ChatGPT 或 API key）。
- WebSearch 无 `debug models` 公开文档 → 属隐藏调试命令，未承诺 API 稳定性。

`codex debug models` 输出（与 `models_cache.json` 数据一致）实测：

|---|---|---|

| gpt-5.6-terra | medium | low, medium, high, xhigh, max, **ultra** |
| gpt-5.6-luna | medium | low, medium, high, xhigh, max |
| gpt-reserve | medium | low, medium, high, xhigh, max |
| gpt-5.5 | medium | low, medium, high, xhigh |
| gpt-5.4 | medium | low, medium, high, xhigh |
| gpt-5.4-mini | medium | low, medium, high, xhigh |
| codex-auto-review | medium | low, medium, high, xhigh, max |

## 推荐方案（Pan 侧改法）

## 第一阶段实现（2026-08-29）

已落地方案 A 的核心部分：

- `CodexAdapter.supported_models` 现在按“显式白名单 → `models_cache.json` →
  `model_catalog_json` → 默认模型”顺序解析；
- 仅展示 `visibility=list` 的模型，隐藏模型不会污染 Pan 的模型选择器；
- `effort_values` 纳入动态目录中声明的 reasoning effort，并保留
  `xhigh` / `max` / `ultra` 等新档位；
- `/api/adapter/config` 额外返回 `modelEfforts`，前端按当前模型联动 effort
  选项；切换模型时若原 effort 不兼容，会自动回到 Codex 原生默认值；
- `_codex_home()` 尊重 `CODEX_HOME`，便于多环境、测试和原生 Codex 配置一致；
- 动态目录损坏、缺失或格式变化时自动回退，不阻断会话创建；
- 新增解析、优先级、可见性、effort 和容错测试。

另外修复了 Codex wrapper 的设置重启路径：模型、权限和 effort 均由 Session
统一编码进 `--codex-extra-args`，不会再把 CBC 风格的 `--model` 等参数误传给
wrapper 的 argparse。

当前仍采用 TTL 缓存（5 分钟），不会为刷新模型列表额外启动 Codex 进程。
模型缓存由 Codex CLI 自己更新；Pan 侧的配置热重载会清空 adapter 缓存。

同时，原生 app-server 的 MCP 启动失败、账号限额变化和模型临时重路由已转换为结构化事件：
前端会提示真正需要用户处理的失败/重路由，额度窗口会显示在顶栏并在 WebSocket 重连后恢复。
原生 `turn/plan/updated` 与 `turn/diff/updated` 也已转换为当前 turn 的实时计划和聚合 diff：
计划在聊天区原位更新，diff 以只读工具卡片展示，并随存活 worker 的 WebSocket 重连回放；
两者均不写入 Pan 的持久 history。

**方案 A（首选）：`supported_models` 新增加读 `~/.codex/models_cache.json` 的优先级。**

```
config.json codex.models 白名单（用户显式限制，保持最高）
  → ~/.codex/models_cache.json（新：官方动态目录）
  → model_catalog_json（cc-switch，现有 _parse_models_from_catalog）
  → 兜底 [default_model]
```

实现要点（对齐现有 `_parse_models_from_catalog` 的容错风格）：
- 新增 `_parse_models_from_models_cache()`：读 `_codex_home()/models_cache.json`，取 `models[].slug`，**过滤 `visibility != "list"`**（剔除 `gpt-reserve`/`codex-auto-review`，与 codex 选择器行为一致），去重保序；文件缺失/解析失败返回 `[]` 走下一级。
- 无需动 5 分钟 TTL 缓存；`invalidate_models_cache` 已覆盖。
- 可选增强：若 `fetched_at` 距今 > 24h 且本机已登录（`auth.json` 存在），spawn 一次 `codex debug models` 强制刷新——**非必需**，因为 codex 自身每次运行都会刷新该文件。

**effort 动态化（两级）：**
1. **最小改动**：codex `effort_values` 扩为完整并集 `["", "low", "medium", "high", "xhigh", "max", "ultra"]`。一行改动，所有模型都能选到；对不支持高档的模型，codex 会拒绝或忽略。
2. **精确联动（进阶）**：`_parse_models_from_models_cache()` 顺带返回 `{model: {default, efforts}}`，前端按所选模型渲染 effort 下拉 + 自动切 default。需动前端（模型→effort 联动），成本较高。

**方案 B（备选，仅当需要强制实时时）：spawn `codex debug models` 解析 JSON。**
成本高：输出 ~300KB（含大段 system prompt）、需登录态、子进程开销。不建议作为默认路径。

**覆盖场景**：`models_cache.json` 覆盖**官方账号**模型；第三方 provider（GLM/DeepSeek 等）走 cc-switch `model_catalog_json`（现有代码已支持）。两者互补，用户切 provider 后 Pan 无需改白名单。

## 证据清单

- 命令：`codex debug models` → 输出 8 模型目录 JSON（含 `visibility`、`supported_in_api`、`default_reasoning_level`、`supported_reasoning_levels`）
- 文件：`~/.codex/models_cache.json`（动态缓存，本次实测随命令刷新至 10:50）
- 文件：`~/.codex/models.json`（3 个 deepseek 自定义模型，非官方源）
- 文件：`~/.codex/cc-switch-model-catalog.json`（cc-switch 产物，config.toml 当前未引用）
- 数据库：`~/.cc-switch/cc-switch.db` providers 表（3 个 codex provider 配置）
- 文档：developers.openai.ac.cn/codex/models（无列举命令，模型可用性依赖登录）

## 决策结果

1. **采用动态方案 A**：显式白名单仍保持最高优先级；未配置白名单时读取
   `models_cache.json`，再回退到 `model_catalog_json` 和默认模型。
2. effort 采用**精确联动**：按当前模型读取支持范围，切换模型后自动清除不兼容的 effort。
3. 文档与实施均在 `feature/codex-models` 分支（worktree `D:/project/pan-codex-models`）进行。
