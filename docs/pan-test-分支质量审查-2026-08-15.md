## 一、问题清单（合并去重，标注来源）

### 🔴 高严重度

#### H1. Stream 模式 result 序号配对语义不一致，中断后 handoff 永久失配【v4p 独有】

三处代码用三种不同计数器表达"任务序号"：
- `handoff` 预分配序号用 `_task_counter`（worker.py:1184-1185）
- MCP 模式 result 的 `taskSeq` 用 `_current_seq`（worker.py:753-754）
- **Stream 模式 result 的 `taskSeq` 用 `_result_count`**（worker.py:314-315）

`handoff` 的 waiter 只匹配 `_task_counter` 序号。`_result_count` 与 `_task_counter` 只有在"每任务恰好一个 result 且严格按序"时才相等。`interrupt/restart/respawn` 中断在途任务、`_consumer_stream` 的 process dead 分支不递增 `_result_count`，都会导致**永久错位**——该 worker 上所有后续 handoff 静默悬挂到超时。MCP 路径已用 `_current_seq`（正确），stream 路径是遗留未同步。`_result_count` 在 MCP 路径是死增量。

**修复**：stream `_read_stdout` 与 MCP 统一用 `w._current_seq`，废弃 `_result_count`。

**现状（2026-08-16 核对）**：❌ **仍存在**——stream 仍用 `_result_count`，MCP 用 `_current_seq`。

#### H2. taskId 幂等注册表：超时+crash 组合永久卡 pending，且无清理【v4f H1 / v4p M2】

- **卡死**：`kill_worker` 和 worker 退出路径只 resolve waiter，**不更新 `_task_status`**。handoff 超时后任务再被 kill → `_task_status[task_id]` 永久停在 pending，重试同 taskId 永远不执行（幂等重试承诺失效）。
- **泄漏**：`_task_status` 是全局 dict，插入后永不删除——无 TTL、无 worker 清理、无大小上限。

**修复**：kill_worker/worker 退出时把名下 pending taskId 标 error；注册表加 TTL 或按 worker 清理；补"超时→kill→重试"测试。

**现状**：❌ **仍存在**——`kill_worker`（worker.py:908）内 `_task_status` 0 次引用，无 TTL。

### 🟠 中严重度

#### M1. 断线重连补发只覆盖"完全未消费"，中途断线丢结果【v4p M1 / v4f L1】

`reconnect` 处理器（server.py:629-640）只在 `consumed_seq[sid] == 0` 时补发 `last_result`；`consumed_seq > 0` 直接跳过。Agent 消费 seq=1 后断线、期间产生 seq 2/3/4 → 全部丢失。且 `last_result` 不存 `taskSeq`，无法精确对齐游标。

**修复**：`last_result` 补存 `taskSeq`；补发条件改 `consumed_seq < latest_seq`，维护可回放环形缓冲（或至少补发最新一条）。

**现状**：❌ **仍存在**——server.py:632 `if sub.consumed_seq.get(sid, 0) > 0: continue`。

#### M2. `_result_waiters` 每 worker 单槽位，并发 handoff 覆盖【v4f M1 / v4p L3】

`_result_waiters[w.worker_id] = (seq, fut)`（worker.py:141）单槽位。并发两个 handoff 打同一 worker → 前者 waiter 被覆盖，前者悬挂至超时（任务本身正常，仅阻塞丢失）。

**修复**：改 `dict[int, asyncio.Future]`（按 seq 索引）或 queue 化；或运行时检测已有 waiter 返回错误。

**现状**：❌ **仍存在**——仍是 `dict[str, tuple]` 单槽位。

#### M3. MCP 模式任务完成后 `last_activity` 未刷新，刚忙完即被回收【v4f M2 / v4p M3】

`last_activity` 更新点只有 `_read_stdout`（stream）、`send_task`、`create_worker` 等；`_consumer_mcp` 全程不刷新。MCP 任务耗时被算进 idle 时长，接近 `timeout_sec` 的任务完成后 watchdog 几乎立即回收。

**修复**：`_consumer_mcp` 置 `status="idle"` 时同步 `last_activity = time.monotonic()`。

**现状**：❌ **仍存在**——`_consumer_mcp` 置 idle 但不刷新 `last_activity`。

## 四、做得好的地方（两份共识）

1. **测试覆盖扎实**：新增 32-34 个用例覆盖状态机、watchdog、三原语、订阅过滤；含关键回归 `test_watchdog_self_cancel_regression`；全量 120 passed。
2. **watchdog 自取消竞态修复到位**：`kill_worker` 用 `current_task()` 判断跳过自取消，有真实 `kill_worker` 回归测试。
3. **zombie 状态可观测**：先广播 `worker.zombie` 再 `workers.pop`，订阅方能观测死亡瞬间。
4. **崩溃/杀死强制 resolve waiter**：EOF、kill_worker、死进程路径均 `_resolve_result_waiter(task_seq=None)` 强制返回 error，避免 handoff 悬挂至超时。

6. **文档质量高**：SKILL.md 详尽、`Meta-Agent实现记录.md` 沉淀了"stream 模式无 init 事件"踩坑。
