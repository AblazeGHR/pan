# Session 持久化修复的性能比较

## 方法与边界

- 基线：`4f10916b`，即已进入 main/practical 的最小死锁补丁。
- 完整修复：`594eba1a`，即异步保存调度、取消保护、已读提交事务与 Web 保存迁移。
- 优化版：在完整修复上增加无 I/O 的 `get_cached`；已读确认命中缓存时绕过共享 store-read executor，未命中仍在线程中浅读取。提交阶段仍检查文件存在，保留删除保护。
- 本机 Windows、Python 3.14.5。同一解释器、同一诊断磁盘目录，独立进程和临时 Session 存储。旧版三个相关模块通过 `git show` 加载；其他依赖相同。交替执行三轮，避免固定顺序偏差。
- 普通保存/增量追加/暖会话 HTTP 每轮 200 次有效样本，预热 20 次；冷会话 HTTP 每轮 30 次，预热 5 次。表中中位数与 P95 都取三轮对应统计量的中位数，并非合并样本的 P95。
- HTTP 使用真实 FastAPI 路由、middleware、JSON 序列化和 broadcast，经过进程内 ASGITransport；关闭诊断请求日志。没有启动应用 lifespan、连接真实 Worker 或请求真实 Session。
- 这是隔离服务端耗时，未包含 TCP、浏览器绘制、真实 provider、杀毒软件极端慢写或全天负载；不能当作生产端到端百分位。

## 影响交互的阻塞场景

三轮中位数，单位 ms。200 ms 是人为设置的固定阻塞，不能解释为线上常见慢写时长。

| 场景 | 最小补丁 | 完整修复 | 优化版 |
|---|---:|---:|---:|
| 无关 store read 阻塞 200 ms 时，缓存会话的已读确认 | 3.545 | 208.834 | 3.310 |
| 已读磁盘写阻塞 200 ms 时，无关健康请求的调度到完成 | 205.575 | 2.162 | 2.112 |
| A 积压 16 次保存且首写阻塞 200 ms，B 的保存 | 209.075 | 1.725 | 1.622 |

最后一项将两版保存 executor 都限制为两个线程，以稳定暴露线程被同会话等待票号占满的情况；不是声称默认 32 线程的生产池会在第 16 次保存时必然阻塞。

完整修复曾将暖已读的内存查找也提交到单线程 store-read executor。这使已读确认排在无关冷读取后面，是这次测量确认的体验退化。优化版只对缓存未命中做 offload，消除了该额外等待。

前端 `selectSession` 不等待已读 ACK 就开始历史请求，`ackSessionUnread` 先乐观清除显示计数。因此 ACK 多出的亚毫秒开销不直接成为聊天内容的等待门槛。对整个前端更有影响的是原同步 ACK 的磁盘等待阻塞所有事件循环请求；新的等待可以与其他请求并行。

## 资源成本

另用 tracemalloc 量化一个会话的 1,000 次排队保存，首写被阻塞，默认线程池配置：

| 指标 | 最小补丁 | 优化版 |
|---|---:|---:|
| 保留的 Python heap 增量 | 5,757,415 bytes | 6,813,396 bytes |
| 每次排队保存的 Python heap | 5,757 bytes | 6,813 bytes |
| 首写仍阻塞时已创建的保存线程 | 32 | 1 |

新结构约多 1.06 KB Python heap/排队保存（1,000 次约多 1.06 MB），主要是排队闭包、Future 与取消保护的协程状态。该数值不包括 OS 线程栈、运行时分配器碎片或其他服务对象，不能据此断言进程 RSS 上升或下降。独立保存池默认上限为 32、懒创建；它与默认 executor 并存，跨很多会话且默认池也繁忙时，总线程上限可能高于旧版。

同会话的终态与已读确认仍需串行等待持久化，这是保持游标正确性的成本。冷缓存未命中仍可能等共享读取线程；文件系统永久不返回时，同会话仍不能完成提交。这些限制没有通过缩短等待或提前发布未持久化状态来掩盖。
