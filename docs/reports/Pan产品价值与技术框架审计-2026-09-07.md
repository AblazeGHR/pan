## 1. 核心判断

Pan 最有价值的潜力，是让用户放心把一项持续数小时、数天、跨工具的工作交出去，并随时知道：成果是什么、依据是什么、下一步需要自己决定什么。

现有多 CLI、持久 Session、异步报告、交接和后台执行已经提供基础。当前最明显的缺口，是产品与代码仍主要围绕“会话如何运转”，尚未充分表达“工作如何完成”。

技术上应继续采用模块化单体，优先重构执行状态归属、持久化事务边界、入口与业务的依赖关系、跨端事件契约。这些比更换框架、拆微服务、扩大插件配置格式更能改善后续开发。

## 2. 产品价值：已有基础与主要缺口

README 中“降低人和 agent 两侧的认知负担”值得作为产品主线。多会话管理、并行编排和多渠道接入都是手段；用户真正需要的收益是：同时推进更多工作，却不需要同比增加监督、解释背景、追问进展和验收的时间。

核心矛盾在于：如果每增加一个 agent，都让用户多读一份报告、多判断一次状态、多处理一次异常，那么并行能力越强，认知负担反而越大。

| 已有基础 | 产品价值 | 当前限制 |
| --- | --- | --- |
| Session 与 Worker 分离 | 执行进程可以更换，协作身份持续存在 | 工作目标、成果与验收状态还不够独立 |
| 持久队列与订阅报告 | 用户和 MA 不必守着执行过程 | 报告送达不代表工作被正确验收 |
| 多 CLI 与 session_handoff | 可按能力、额度、上下文调整执行者 | 交接质量依赖摘要的完整性和可信度 |
| manifest、MCP、外部服务接入 | 能承载领域方法和工具 | 配置接入尚未形成完整的工作流运行契约 |

依据：[Session 模型](../../packages/core/session.py)、[执行与报告](../../packages/core/worker.py)、[manifest 数据结构](../../packages/core/manifest_loader.py)。

建议更集中地表达产品定位：**把复杂工作交给一支可接管、可恢复、成果可追溯的 AI 团队。** 用户长期使用的理由应落在工作结果与注意力节省上。

## 3. 怎样产生令人惊艳的体验

首次体验应是一个完整的小闭环：用户提供目标与材料，Pan 给出少量关键选择；确认后自主推进；用户离开再回来时，看到可打开的成果、验证依据、未解决的问题和下一项必要决定。即使中途更换执行者，也不用重新交代背景。

### 3.1 增加工作视图

当前主路由围绕聊天、编辑器、会话管理组织，状态结构主要围绕 Session 和 Worker。这适合操作台，但不足以让用户理解多项工作的全局状况。

工作视图需要回答：

- 我委托了什么，目标是否变化？
- 哪些成果已验收，哪些只是 agent 声称完成？
- 工作被什么阻塞，是否需要我处理？
- 已投入多少时间与资源，还需要投入多少？
- 从哪里查看证据、调整方向、暂停或接管？

会话与进程信息可以逐层展开。不要用 Worker 忙闲状态推算业务进度，也不要用未经校准的百分比制造确定感。证据不足、审美选择、集成失败等领域状态，比“几个 Worker 正在运行”更有意义。

依据：[路由](../../packages/web/src/router.tsx)、[Session Store](../../packages/web/src/stores/sessionStore.ts)。

### 3.2 将等待用户回复建模为决策对象

原生 CLI 审批与输入请求已有桥接，但允许工具调用和选择项目方向属于不同层次的交互。

产品级决策应包含：需要人的原因、可选方案、推荐依据、受影响成果、是否阻塞其他工作。回应应成为后续执行与交接的持久依据。

Pan 可以进一步管理用户注意力：合并相关决定，延后不阻塞执行的问题，及时提示真正阻塞的事项，让多 agent 的复杂性在到达用户前被消化。

### 3.3 将成果与验收建模为可操作对象

聊天中的“已完成”和文件链接不足以支撑长期协作。成果至少应有稳定标识、版本、来源、对应目标与验证记录。

| 领域 | 成果 | 验收依据 |
| --- | --- | --- |
| 软件工程 | 变更、构建、可运行功能 | 测试、真实行为、评审与部署状态 |
| 科研 | 结论、数据、实验记录 | 来源、方法、可复现性、反例与不确定性 |
| 艺术设计 | 方案、资产、成品 | 约束满足、版本比较、人工审美选择 |

通用内核记录验收结论与证据，不应把测试通过写成所有工作的完成定义。自动检查、agent 评审、用户选择要保留各自来源。

### 3.4 让失败恢复可解释

恢复不能只表现为重新启动进程。用户应能理解哪些成果保留、哪个动作结果不确定、系统正在核对什么，以及何时可以继续。

不能用自动重试掩盖重复提交、重复发送、重复扣费等外部副作用。诚实且可解释的恢复，是长期信任的重要组成部分。

## 4. 尚未充分挖掘的潜力

以下均为待验证产品假设。

### 4.1 工作流插件承载专业方法

科研插件应提供从问题走到证据与结论的方法；设计插件应提供从需求到方案比较、迭代与交付的方法。

插件需要说明输入材料、推进方式、动态调整范围、工具与权限、产出与验收、失败处理和人工介入条件。SessionTemplate 解决打开特定会话，WorkflowDefinition 解决持续推进一类工作，两者应组合。

### 4.2 工作跨执行者、跨方法持续存在

同一工作可以先调研、再实验、再产出设计或代码，各阶段复用已确认事实、决策与成果。长期积累的价值在于成果关系与决策依据。

当上游约束变化时，未来可以指出哪些下游成果需要重检。无需立即实现完整依赖失效系统，但应避免将这些关系只埋在聊天中。

### 4.3 工作流从真实交付中改进

记录常见返工点、有效验收证据和重复出现的人工决定后，系统可以提出具体流程改进，例如提前检查经常缺失的材料。这需要真实执行与验收数据，现阶段不宜先建设庞大的自动优化系统。

商业化同样需要验证：个人用户可能重视跨设备、长任务托管和高质量模板；团队可能重视共享成果、治理和协作。目前没有用户与付费证据支持确定路线。

持久化和中断恢复已有外部框架实现，因此这些机制本身不足以构成充分差异。Pan 需要将它们转为可感知的交付体验。参考：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。这不是引入或迁移到该框架的建议。

## 5. 附件的适用边界

值得吸收的原则：

1. 委托有目标、范围、预算与升级条件。
2. 执行完成与验收通过分开。
3. 智能负责判断，运行系统负责记录与约束。

不宜直接进入通用内核的内容：固定五小时周期、固定 MA/TA 阵型、SWE 状态枚举、Git 合并语义、四份固定文档。

附件的四类事实来源可以作为 SWE 插件的信息分类，但每类事实仍需明确的权威归属。不能让 ROADMAP、任务表、聊天总结和 STATE LEDGER 独立改写同一个任务状态。

建议插件定义关键约束与验收节点，agent 在约束内动态规划，Pan 持久记录计划变化、执行结果和人工决定。科研和设计不必预先展开成固定 DAG。

## 6. 技术框架审计梗概

核心问题是模块职责和状态归属。新增行为往往需要同时修改进程、队列、存储、API 和前端，开发成本会持续上升。

基线文件总行数（包含空行与注释）：`worker.py` 5,426 行、`web/server.py` 5,265 行、`session.py` 1,123 行、`useWebSocket.ts` 826 行。行数只是规模信号；关键证据是业务修改跨越多个责任边界。

| 优先级 | 方向 | 收益 |
| --- | --- | --- |
| 第一批 | 执行内核与应用服务边界 | 业务规则不再散落于入口、Worker 与队列私有函数 |
| 第一批 | 持久化事务与完成事件 | 明确崩溃恢复依据，减少跨对象不一致 |
| 第二批 | 统一事件与读取模型 | 减少厂商差异和前端竞态处理 |
| 第二批 | 统一调用身份与策略入口 | 为委托授权和插件能力限制提供基础 |
| 随产品验证推进 | 独立工作模型与插件运行契约 | 支撑跨领域扩展，避免扩大 Session |

### 6.1 拆出执行内核与应用服务

`worker.py` 同时负责队列预留投递、报告路由、恢复调度、进程启停、历史写入、记忆注入和原生交互。`server.py` 直接调用大量 `worker._...` 私有函数，并自行改队列、保存 Session 和广播。

建议职责划分：

- Mailbox/Delivery：队列顺序、幂等身份、预留、回执与重试。
- Runtime Supervisor：Worker 注册、代次、启停、接管和异常恢复。
- Turn Executor：执行一轮输入、接收标准事件、报告交接边界。
- Report Service：完成事实到订阅收件箱的投递。
- Application Service：派发、交接、修改队列等完整业务操作。

HTTP、MCP、WS 入口解析请求并调用应用服务，由业务层决定权限检查、状态变更、落盘和事件产生。验收标准是新增入口无需复制恢复逻辑，修改队列规则无需修改 HTTP 层的私有函数调用。单纯分割长文件无效。

保留 `queue_pending` 的队列事实地位，以及 `pending_signal` 只负责唤醒的语义。计时器、锁、进程句柄和当前代次状态仍属于临时 Worker，不应整体迁入 Session。

依据：[Worker](../../packages/core/worker.py) 的 `_reserve_queue_unit`、`_commit_queue_handoff`、`_enqueue_report`；[HTTP 服务](../../packages/web/server.py) 的队列处理；[执行状态归属测试](../../tests/test_execution_state_ownership.py)。

### 6.2 从保存对象提升为提交业务变化

现有增量历史、锁和原子替换值得保留，但单文件原子写不等于跨文件事务。

- handoff 依次保存新会话、子会话、父会话、订阅和旧会话，中途崩溃存在部分关系转移风险。
- 正常完成先保存结果，再广播并写入主管队列，步骤间存在崩溃窗口。本次未见该路径具有与 Background Job 同等明确的持久 outbox 补投机制；这属于静态风险判断，尚未进行故障复现。

Background Job 已有可借鉴模式：先记录终态和稳定事件 ID，再投递通知、记录投递状态。

建议先建立 Repository 与事务接口，再评估将关系、队列元数据、任务记录、outbox 等控制状态迁入 SQLite。大量历史与日志可继续使用文件。若保留文件存储，需要操作日志和恢复协调器承担对应职责。数据库选择不是第一步。

CLI handoff 回执保存失败后，当前代码会安排重试。本地任务 ID 不能保证外部动作恰好执行一次；数据库事务也无法消除“外部已执行、本地未确认”的窗口。应区分安全重试、外部幂等键、查询核对和不确定结果待处理。

依据：[会话存储与交接](../../packages/core/session.py) 的 `_save_sync`、`handoff_session`；[结果处理](../../packages/core/worker.py) 的 `_read_stdout`、`_commit_queue_handoff`；[后台通知](../../packages/core/background_jobs.py) 的 `runner_update`、`recover_notifications`。

### 6.3 工作独立于会话

Session 已包含身份、配置、管理关系、历史、队列、用量和领域字段；`game_id` 是领域信息进入核心的直接例子。

| 概念 | 职责 |
| --- | --- |
| Work / Run | 用户委托及一次工作的推进状态 |
| Task | 具体责任单元 |
| Attempt | 某执行者的一次尝试 |
| Artifact / Evidence | 成果与结论依据 |
| Decision | 决策者、输入依据和决定 |
| Session / Worker | 持久 agent 身份与临时执行进程 |

保留 Session 的现有身份语义。`taskId`、`task_seq` 和投递 ledger 是基础，尚不能等同于完整业务任务模型。先围绕真实闭环实现 Run、成果引用和验收结论，使换 Session 后任务身份不变，新尝试不会继承旧 Worker 的临时运行状态。

### 6.4 统一事件与前端状态契约

前端事件类型包含多个厂商原生字段。`useWebSocket` 同时处理原生交互、流式合并、会话和队列刷新、多 Store 更新；Session Store 使用触碰序号、历史前缀比较等手段处理 HTTP 与 WS 交错。

建议在 adapter 边界产生标准消息、执行、交互和完成事件；原生字段保留在专用扩展载荷中。补齐稳定消息 ID、执行代次、事件 ID、相关实体版本，让快照与事件遵循相同的版本规则。

重要业务状态应能重建，流式显示可保留临时增量。可推广队列现有的“服务端快照为真、事件提示刷新”模式，无需将每个 token 变成持久业务事件，也无需全系统事件溯源。

依据：[事件类型](../../packages/web/src/types/index.ts)、[WS 处理](../../packages/web/src/hooks/useWebSocket.ts)、[Session Store](../../packages/web/src/stores/sessionStore.ts)。

### 6.5 统一策略入口并明确强制能力

`pan_access` 主要承担 MCP 会话管理限制。MCP 身份来自环境变量，缺失或无法解析时按外部协调者放行；HTTP 来源校验承担另一类职责。当前可信本地工具模型不能直接当作强制 Autonomy Lease。

如果产品要承诺插件权限与委托范围，就需要统一调用上下文，明确调用者、目标、操作和授权，让 HTTP、MCP、WS 经过同一应用策略。来源字段用于追溯，不能替代可信身份。

Pan 只能约束经过自身的动作。CLI 直接执行文件、网络、数据库操作，需要执行环境、凭证或 sandbox 配合。worktree 提供协作隔离，不自动形成文件权限隔离。这是产品承诺边界，不是立即建设完整沙箱平台的要求。

依据：[MCP 身份与访问检查](../../packages/mcp/server.py) 的 `_caller_identity`、`_check_access`；[HTTP 来源检查](../../packages/web/server.py) 的 `_request_source_metadata`、`_source_access_error`。

### 6.6 分层演进插件契约

manifest 当前按名称合并，后加载覆盖先加载。第三方生态需要明确冲突归属、版本与运行兼容性。

先补插件稳定 ID、命名空间、schema 版本、能力声明、安装诊断和运行绑定的定义版本，避免更新插件时悄悄改变运行中的验收规则。之后再增加工作流输入输出、检查点、恢复行为与验收扩展。

复杂领域状态应有自己的权威存储，Pan 保存运行关系与必要证据引用。区分模板、外部工具服务和可执行扩展的权限与故障边界；早期优先复用 MCP/外部服务，任意进程内代码插件会增加生命周期和兼容成本。

依据：[manifest 加载](../../packages/core/manifest_loader.py) 的 `load_manifests`、`_merge_manifest`。

## 7. 推进顺序与验收

建议以真实业务操作逐步替换内部实现，避免覆盖全项目的大重写。

| 阶段 | 工作 | 完成依据 |
| --- | --- | --- |
| 建立重构支点 | 派发、报告、交接的业务服务与状态归属 | 入口不再直接拼装内部步骤 |
| 固化可靠性 | 完成事件 outbox、事务边界、故障窗口测试 | 崩溃后能区分已提交事实与待补投、待核对动作 |
| 产品闭环 | 工作视图、成果、验收、决策 | 用户完成委托验收时少读执行细节 |
| 验证通用性 | 用轻量非 SWE 工作流检验模型 | 无需新增 Session 领域字段即可完成闭环 |
| 开放插件契约 | 命名空间、版本绑定、诊断与兼容边界 | 插件更新和失败不破坏已有运行 |

现有队列、handoff、状态归属、后台任务和前端竞态测试值得保留。后续补充跨持久化步骤故障注入、不同入口的同业务契约测试，以及真实进程退出和浏览器重连测试。测试文件存在不代表场景已经通过；本次没有执行。

建议衡量产品效果：首次合格成果所需时间、每项合格交付的人工注意力时间、遗漏与返工、恢复时重新解释背景的次数、非预期重复执行与漏报、每项合格成果的资源成本。

近期若只能推进两项，建议选择：贯穿派发、完成、报告的应用服务与持久化重构；围绕工作、成果和决策的完整用户闭环。前者降低后续实现成本，后者验证用户是否愿意放心委托更多工作。SWE、科研和艺术设计插件的共同契约，应从真实使用中提炼。
