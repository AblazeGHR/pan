## 一、聊天气泡左右分栏

### 1.1 问题

聊天区原先 user 与 assistant 都是整宽排版，仅靠左侧 3px 颜色条区分角色（user 绿 `--color-success`、assistant 灰 `--color-text-secondary`）。上下翻找历史时很难一眼分辨「哪条是我发的、哪条是回答」。

### 1.2 改动

| 文件 | 变更 |
|------|------|
| `packages/web/src/components/chat/MessageBubble.tsx` | user / assistant 两处外层加 `message-row message-row-user` / `message-row message-row-assistant`，去掉 `w-full`；时间戳随之自动贴边 |
| `packages/web/src/index.css` | 新增 `.message-row` flex 分栏；user 右对齐 `max-width:75%`、accent 调色背景；assistant 左对齐 `85%`、`bg-tertiary`；窄屏（<640px）放宽到 94%/96%；删除旧的整宽规则与 `>` 前缀 |

落进构建产物的关键规则：

```css
.message-row{flex-direction:column;min-width:0;display:flex}
.message-row-user{align-items:flex-end}
.message-row-assistant{align-items:flex-start}
.message-row-user .msg.user{max-width:94%}          /* 窄屏档 */
.message-row-assistant .msg.assistant{max-width:96%}
```

### 1.3 关键约束

- **虚拟化测量不能被破坏**：行内垂直间距必须用 padding（`pt-*`）而非 margin —— margin 在 measured virtual row 里会 collapse，导致高度缓存错误、行重叠。水平对齐改用 flex + `align-items`，不动行 wrapper 的宽度与 style 逻辑。
- **深浅主题都要可读**：颜色一律走 `index.css` 已有的 CSS 变量（`--color-accent` / `--color-bg-tertiary` / `--color-border-default` / `--color-bg-secondary`），不硬编码十六进制。主题机制是 `data-theme` 属性，`:root` 为深色，`[data-theme="light"]` 覆盖为浅色。
- 长代码块 / 宽表格不得撑破气泡。

## 二、会话滚动：分页跳动

### 2.1 问题

向上滑动会话时滚动不平滑；滑到顶部触发加载更早上文（`scrollTop <= 200` 触发 `loadOlderMessages()`）时，页面发生明显跳动。

### 2.2 根因

1. **位置恢复的时序竞争（主因）**：`ChatMessages.tsx` 在 `loadOlderMessages()` 的 promise resolve 后，用**单个** `requestAnimationFrame` 读 `scrollHeight` 补 `scrollTop`。那一刻 React 可能尚未提交新列表；即便已提交，`@tanstack/react-virtual` 也还没测完新插入的行 —— 新行先按 `estimateSize: 100` 撑开，随后由 `measureElement` 异步实测，`getTotalSize()` 与 spacer 的 `minHeight` 在**后续几帧又变一次**。于是「恢复完再抖一下」。
2. `style={{ overflowAnchor: 'none' }}` 显式关闭浏览器原生 scroll anchoring，使手工恢复成为唯一机制，算错就没有兜底。
3. 行用 **flow margin**（`marginTop: flowOffset`）而非绝对定位，任何 `vItem.start` 变化都会推移后面所有行。
4. `estimateSize` 恒为 100，长消息误差大，恢复公式实际用的是「估计高度」而非最终高度。

### 2.3 改动（仅 `ChatMessages.tsx`，+97 / −16）

- 分页锚点从「虚拟器估算高度」改为保存**真实渲染行元素**及其 `getBoundingClientRect().top`。
- 新增 `restorePaginationAnchor()`：用真实行几何修正 `scrollTop`；jsdom 无几何时回退到原 height-delta 路径（保证单测有效）。
- 新增 `schedulePaginationRestore()`：跨帧持续修正，直到 `scrollHeight:scrollTop:anchorTop` 签名连续 2 帧稳定（上限 30 帧），覆盖「测量晚于恢复」的窗口。
- 新增 `useLayoutEffect`：在浏览器 paint 前先恢复一次。
- 触发分页时捕获视口内第一个 `[data-index]` 行作为锚点。
- 切换会话时取消挂起的恢复 rAF。

### 2.4 验证数据

worker 自测（真实会话 `fe-chat-split-bubbles`，`historyTotal: 58`）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 参照行最大偏移 | **154px** | 0.359px |
| 单帧最大跳变 | 154px | 0.359px |
| >8px 跳变次数 | **2** | 0 |
| scrollHeight 轨迹 | 4377 → 6631 | 4425 → 6679 |

SMA 独立复现（不同窗口尺寸，`clientHeight: 475`，180 帧采样）：

```
maxAbsOffset: 0px     maxFrameJump: 0px     jumpsOver8px: 0
scrollHeight: 3815 -> 5565    （期间确实发生了 +1750px 的上文插入）
```

采样期间插入 1750px 内容，参照消息**逐帧位移恒为 0**。

**回归保护**：后续第三、四轮改动都复用/经过这条路径，每轮都复测过 —— 最终仍为 `maxAbsOffset: 0 / maxFrameJump: 0 / jumpsOver8px: 0`（期间 scrollHeight 5374 → 10593）。

### 2.5 未覆盖 / 残留风险

## 三、快速定位导航轨

### 3.1 需求

给会话加快速定位：标记**用户发送**与 **worker report** 两类「我们这边发出去的内容」（两类要能区分开），会话边缘加按钮可快速跳转查找，鼠标悬停能预览内容片段。

### 3.2 消息语义（实现依据）

`packages/web/src/components/chat/messageFilter.ts` 中的前缀常量（本次改为导出，供复用）：

| 常量 | 值 | 含义 |
|------|-----|------|
| `META_AGENT_PREFIX` | `////by agent` | meta-agent 编排消息（发给 TA 的指令） |
| `TASK_AGENT_PREFIX` | `@@@@by agent` | **task-agent 完成报告 = 用户说的 worker report** |
| `QQ_PREFIX` | `@@@@by qq` | QQ 注入消息 |

判定与角色无关，全部基于 `content.trimStart()` 前缀匹配。**worker report 优先于 role 判定** —— 某些 adapter 会把报告序列化成 user 消息。

新增：`getQuickJumpKind(message)` / `getQuickJumpPreview(content, maxLength=120)` / `getQuickJumpMessages(...)` / 后续的 `getQuickJumpIndexItems(...)`。

`getQuickJumpPreview` 会剥掉 `@@@@by agent : <session> | <name>` 这类 transport header，再把空白归一化并截断。

### 3.3 实现

新增 `packages/web/src/components/chat/MessageNavigationRail.tsx`（聊天区右边缘导航轨）：

- 顶部两个筛选按钮：`用户` / `Worker`，各带计数徽标。
- 轨上每个 target 一个 `<button>`，两类用**不同颜色 + 不同图标**（`UserRound` vs `Bot`）。
- 悬停 → `createPortal` 到 `document.body` 的 `.message-navigation-tooltip` 浮层，显示类别标签 + 预览片段。
- 点击 → 跳转并高亮（`.chat-message-jump-highlight`，约 1.2–1.4s 后自动消失）。
- `ChatMessages.tsx` 改为 `forwardRef` 并暴露 `ChatMessagesHandle.scrollToMessage(message, historyIndex)`。

### 3.4 筛选是互斥的（有意的设计取舍）

实测：默认 `用户` 激活；点 `Worker` 切成只显示 worker 标记；**再点 `Worker` 不取消**。也就是**无法同时看到两类标记**。用户已确认：**「筛选互斥没有关系」**，保留现状。

实测颜色（随主题自适应）：

| | 文字色 | 背景 | 边框 |
|---|---|---|---|
| 深色 | `rgb(63,185,80)` | `srgb(0.107,0.186,0.157)` | `srgb(0.216,0.458,0.275)` |
| 浅色 | `rgb(26,127,55)` | `srgb(0.853,0.911,0.881)` | `srgb(0.489,0.692,0.565)` |

### 4.2 问题 B：导航轨只显示已加载的对话

**机制现状**（不是「保存上下文」，而是**滑动窗口 + 懒加载**）：

1. `sessionStore.selectSession()` 只拉**最近 50 条**（`fetchSessionHistory(id, 0, 50)`）存进 `currentMessages`。
2. `historyLoadEnd = historyTotal − 已加载数`。
3. 只有滚到 `scrollTop <= 200` 才触发 `loadOlderMessages()` 再拉一页（`limit=50`），用 `[...older, ...current]` **前插**合并。
4. 导航轨的输入原本是 `currentMessages` → **只能标出已滚过的那部分**。

**关键设计点**：因为合并方式保证**窗口尾部永远钉在最新一条**，所以 **`fromEnd`（距末尾偏移量）是一条消息不变的稳定身份**，而数组下标会随加载前移、不能当主键。绝对索引 `i` 的消息对应 `fromEnd = total - 1 - i`。

后端接口（已读源码确认）：`GET /api/sessions/{id}/history?before=N&limit=M`，`before <= 0` 视为 `total`，返回 `{history, total, hasMore, start}`，`start = max(0, before - limit)`；向后翻页传 `before = start`。

**改动**：

- `sessionStore.ts` 新增 `ensureMessageLoaded(fromEnd, total)`：连续拉页直到 `historyLoadEnd` 覆盖目标，返回目标消息或 `null`（**明确失败，而非静默跳到错误位置**）。
- `MessageNavigationRail.tsx` 进入会话时后台异步遍历分页（`INDEX_PAGE_SIZE = 200`），**渐进**构建 `{fromEnd, kind, preview}` 索引；`AbortController` 在会话切换时取消；失败降级回「仅已加载窗口」并显示错误指示器。
- 诊断数据暴露为 data 属性：`data-index-status` / `data-indexed-targets` / `data-history-total` / `data-index-requests` / `data-index-duration-ms`。

### 4.3 验证证据（SMA 独立实测）

|---|---|

## 五、气泡横向溢出修复

### 5.1 问题

「有的气泡最右端会超出屏幕范围」—— 内容横向溢出，且**只在部分消息上出现**。

### 5.2 真正的根因（worker 实测得出，推翻了任务简报里的三条假设）

**flex `min-width: auto` 撑爆**：

1. `ChatMessages.tsx` 的根列 `flex-1 flex flex-col min-h-0 relative` 作为 flex item 默认 `min-width: auto`，**拒绝收缩到 min-content 以下**。
2. 含不可断 token 的消息（URL / 路径 / 行内 `code` / 长中英混排）把该列撑到 **2462px**（父容器仅 1180px）。
3. 滚动容器继承该宽度（`clientWidth` 1112 → **1391**）。
4. `.msg { max-width: 75% }` 于是**对着被撑大的行**（1390.5px）计算而不是视口 → 气泡 994.9px 画到 `x=1618.5`（1440 视口）→ **超出屏幕 178.5px**。

这解释了「为什么只命中部分消息」：**同一行在 scroll-top 时 `rowW=1112` 正常，在 scroll-bottom 时 `rowW=1390.5` 溢出** —— 状态相关。

**被排除的假设**（都测过，均不成立）：

| 假设 | 结论 |
|---|---|
| KaTeX `.katex { white-space: nowrap }` 溢出 | **不成立**。`remark-math` 不是依赖、`katex.min.css` 从未 import（`katexCssRules: 0`），`rehype-katex` 输出是死代码，`$…$` 渲染成字面文本 |
| `width: fit-content` + `max-width: %` | 不是触发点 |
| `fit-content` 气泡里的表格 `width:100%` | 不是触发点 |
| 长 token（URL / 路径 / 行内 code） | **是触发器**，不是根因 |

### 5.3 修复

`packages/web/src/components/chat/ChatMessages.tsx:355` —— **加一个 class**：

```diff
+    // `min-w-0` is load-bearing. As a flex item this column defaults to

+    // inline code) can stretch the column to its min-content width. The bubble's
+    // `max-width: 75%/85%` then resolves against that inflated row instead of
+    // the real viewport, painting the bubble past the right screen edge.
-    <div className="flex-1 flex flex-col min-h-0 relative">
```

### 5.4 一个必须记录的验证方法漏洞

`body` 上有 `overflow-x: hidden`，所以**即使气泡画到屏幕外几百 px，文档级 `scrollWidth > clientWidth` 依然是 0**（溢出被画在了屏幕之外，不产生滚动条）。

**第一轮验收气泡功能时用的判据正是「文档 `scrollWidth > clientWidth`」，因此那个方法根本不可能发现这个 bug。**

✅ 正确判据：

1. 每个元素 `getBoundingClientRect().right` vs `window.innerWidth`；
2. 滚动容器自身的 `scrollWidth` vs `clientWidth`；
3. 元素自身 `scrollWidth` vs `clientWidth`（内容逸出盒子）。

## 六、视图切换回 Chat 的位置跳动

### 6.1 问题

「点击右侧导航轨可以正常定位跳转，但是切到别的页面再重新切回来网页就会莫名跳动。」

SMA 复现后发现**范围比原描述更广**：这不是「导航跳转后」才有的特例 —— **只要用户不在底部就不行**。对照组证明：完全不使用导航、手动滚到中间位置，切走再切回同样被拽到底部。用户之所以觉得是「导航跳转后才有」，只是因为只有那时才会停在非底部位置。

### 6.2 根因（两条，缺一不可）

1. **`ChatView` 卸载 → `ChatMessages` 重新挂载，而 `currentSessionId` 没变**。挂载时 `shouldFollowBottomRef = useRef(true)`、`initialScrollPendingRef = useRef(true)` 都回到初始值，且依赖 `[currentSessionId]` 的会话切换 effect **在 id 没变的情况下也会跑一遍** → 挂载即 `scrollToBottom()`。
2. **重挂载的 virtualizer 丢掉了上次的实测行高**，退回 `estimateSize: () => 100` 兜底，滚动位置必然漂移（实测 `3519 → 3471`）。

典型的可见位移是**两段**：先落到旧位置附近，再跳到最新消息。

### 6.3 改动（仅 `packages/web/src/components/chat/ChatMessages.tsx`，约 +150 / −5）

- **会话级滚动快照**（模块级 `Map<sessionId, snapshot>`）：锚点用**虚拟内容坐标**（`rect.top - viewport.top + scrollTop`），不受虚拟窗口与整体重测影响；快照带**列表指纹**（条数 + 首/末 item key）并**一次性消费**（挂载判定即 `delete`）。
- **挂载时的一次性判定**：仅在 `activeSessionId === currentSessionId`（同一会话重挂载）且指纹一致时启用恢复。
- **`estimateSize` 优先取缓存的实测行高**（卸载时写入），消除重挂载漂移。
- **真正的 bug 修复点**：`shouldFollowBottomRef` / `initialScrollPendingRef` 的初值改为 `!isRestoringRef.current`（`ChatMessages.tsx:104-106, 213-218`）。
- **还原**：新增 `useLayoutEffect` 在 paint 前校正；落定后把锚点交给**既有的** `paginationAnchorRef + schedulePaginationRestore()` 逐帧校正循环；`shouldFollowBottomRef` 按实际距离底部的距离重算。
- **守卫**：会话切换 effect 加 `handledSessionRef`，同一会话的重复运行直接返回（不改变任何既有场景）；真正切会话时**主动删除**该会话的旧快照与旧行高。
- **坑**：导航轨 `scrollToIndex` 的程序化跳转**不触发容器 scroll 事件**，导致「跳转后立刻切走」记下的仍是跳转前旧位置 —— 已在 `scrollToMessage` 里补一次双 rAF 刷新。

### 6.4 「① 保持位置」与「② 切会话必须到最新」如何不冲突

二者靠**三个互相独立的判据**分开，而非同一分支：

1. 恢复只在 `activeSessionId === currentSessionId`（同会话重挂载）时启用；真正的会话切换走会话切换 effect，并**主动删除**旧快照与旧行高。
2. 快照带列表指纹且一次性消费 —— 历史变了或不是紧接着的那次挂载都不会还原。
3. `shouldFollowBottomRef` / `initialScrollPendingRef` 的**初值**只在恢复态下为 `false`；会话切换路径本身会显式把它们置 `true`。

## 七、焦点恢复（切到别的网页再切回）的跳动

> 用户报告：导航定位后**就算等一分钟**，切到别的**网页**（不是换 session）再切回，依旧页面跳动。
> 注意「切到别的**网页**」= **另一个浏览器标签页 / 应用窗口**，会触发焦点与可见性变化 —— 这是前六轮**从未覆盖**的场景（此前所有验证都是在同一标签页里点路由链接）。

### 7.1 真正的根因

```
切到别的网页（visibilitychange / focus / pageshow）
  → useWebSocket 的 recover()（延迟去抖后执行）
  → refreshCurrentSessionHistory() → fetchSessionHistory(sid, 0, 50) 拉最新 50 条
  → currentMessages 被整体替换                ← 问题在这
  → virtualizer 重新测量
  → overflowAnchor: 'none' 无法提供浏览器原生补偿
  → 可见跳动
```

旧的 `isServerHistoryPrefix()` 只保护「流式回复尚未落盘」这一种情况（服务端历史是本地历史的**前缀**），**不保护「本地已加载了分页窗口」**：用户点导航跳到老消息后，本地窗口远大于最新 50 条，焦点恢复一刷新就被裁掉。

### 7.2 改动（仅 `packages/web/src/stores/sessionStore.ts`，+31 / −3）

新增 `sameMessage()` 与 `mergeRefreshedHistory(localHistory, serverHistory)`：

1. 服务端是本地前缀 → 保留本地（原有流式保护，行为不变）；
2. 服务端为空 → 保留本地；
3. 否则找本地尾部与服务端窗口的**最大重叠**：完全重叠 → 保留本地；尾部前进了 → **只追加新增部分**；
4. 无法建立可靠重叠才回退到服务端历史；
5. 合并成功时**保留原 `historyLoadEnd`**（分页坐标不被重置）。

同时 `focus` 恢复路径改为使用合并结果：

```ts
const mergedHistory = mergeRefreshedHistory(current.currentMessages, serverHistory);
currentMessages: mergedHistory ?? serverHistory,
historyLoadEnd: mergedHistory ? s.historyLoadEnd : data.start,
```

**同轮附带的提速**（前一轮遗留）：`loadOlderMessages` 增加 `limit` 形参（默认 50，普通滚顶分页不变）；`ensureMessageLoaded` 按「距目标的剩余跨度」发**一次有上限的请求**（单次上限 1000）。

### 7.3 验证数据（SMA 真实触发该路径）

真实会话 `math`（1301 条）→ 导航跳到最老消息 → 等稳定 → **派发真实 `focus` 事件**（`window.addEventListener('focus', recover)` 是直接监听，合成事件可命中，与 React 合成事件不同）：

```
focus 恢复期间 /history 请求：1 次（确实走了 refreshCurrentSessionHistory）
360 帧逐帧采样：
  scrollTop    恒 0
  scrollHeight 恒 110396   （shMin === shMax —— 分页窗口未被裁掉）
  参照行 refTop=152 恒定 —— 位移 0，单帧跳变 0，>8px 0 帧
  参照行始终在 DOM
```

**焦点恢复拉了新数据、合并进本地窗口、全程零跳动。**

**跳转提速**（前一轮遗留问题一并解决）：

| | 修复前 | 修复后 |
|---|---|---|
| 跳转请求数 | 26 次（50 条/页串行） | **1 次**（按剩余跨度一次请求，单次上限 1000） |
| 跳转耗时 | 约 11 秒 | 约 2 秒（实测稳定耗时 4.4s，含 2.5s 轮询等待开销） |

**加载窗口内切走**（0.5s / 1s / 2s 三个时间点实测）：切回后都落在目标位置（`st=0`），**不再回退到底部**，`>8px 0` 帧。

### 7.4 未覆盖 / 已知边界

- **真实双标签页切换的端到端逐帧数据未完成**：worker 的双 target 脚本没能真正点中会话卡片（侧栏滚动越过了目标）；CDP `Page.setWebLifecycleState` 在 Edge 上不产生 `visibilitychange`/`blur`/`focus`，不等价。已改用「派发真实 focus 事件」覆盖同一条代码路径。
- **离开期间有新消息**的分支（合并逻辑第 3 条）由代码路径覆盖 + 单测保护，**未在真实环境凭空制造一条新消息来测**。
- `useVisualViewport` 的 resize/focus 注入未单独实测（诊断表标记 N/A，本次未改该 hook）。
- Tasks / Manage / 快捷键 / CommandPalette 等入口仍未逐条实测。

## 八、方法论与工具沉淀

### 8.1 本机环境事实（每次验证前端都会踩）

- `packages/web/node_modules` **存在**，`vite` / `vitest` / `typescript` / `.bin/tsc` 齐全 → build 与 vitest 可直接跑。**仓库根目录与 `packages/core/` 的 node_modules 不存在**，据此误判成「依赖没装」会白折腾一轮。
- **pnpm 不可用**，一律用 `npm run` / `npx`。
- `@playwright/test` 虽在 `package.json` 声明，**本机未安装**，也没有 playwright CLI；现有 `e2e/run-browser.mjs` 等套件因此跑不起来。不要为此 `npm install`。
- `vite.config.ts` 的 `root` 是 **`'src'`**（不是 `packages/web`），静态 HTML 放错目录会被 SPA fallback 吃掉。
- 主题通过 `data-theme` 属性切换，不是 class。
- **Edge headless 最小布局视口 496px**，更窄的请求会被钳制。

### 8.2 无 playwright 时的浏览器验证路线

**mock 模式造数据**：`http://127.0.0.1:8768/react/?mock=1`（纯前端，不碰后端）。先打开该页 → 注入 `localStorage['pan:mockSessions'] = JSON.stringify([{id,name,adapter:'cbc',workerStatus:'idle',historyTotal,history:[...]}])` → reload → **点击 `[data-session-card-id]`**（只注入不点击不会挂载消息行）。

**CDP 驱动**：

1. 启动 `msedge --headless=new --user-data-dir=<临时目录> --remote-debugging-port=<空闲端口>`。
2. `PUT http://127.0.0.1:<port>/json/new?url=<目标>` 拿 `webSocketDebuggerUrl`。
3. Node 24 自带原生 `WebSocket`；用 `Runtime.evaluate({awaitPromise:true,returnByValue:true})` 驱动；`Emulation.setDeviceMetricsOverride` 模拟视口。

**逐帧滚动测量**：注入 `requestAnimationFrame` 采样循环，逐帧记录参照元素 `getBoundingClientRect().top` 与容器 `scrollTop`/`scrollHeight`，离线算最大偏移、单帧跳变、>8px 次数。**基线必须在程序化滚动之后取**，否则会把程序化跳转本身算成偏移。

**因果开关实验**（本轮新增，强烈推荐）：当 worker 声称「一个属性就能修好」时，**在浏览器里运行时增删该 class** 并前后测量。确定性的翻转比 before/after 文件快照强得多，而且**不需要 stash 脏工作区**。

静态视觉检查更省事：`msedge --headless=new --screenshot=<out.png> --window-size=W,H <url>`；需要读取注入脚本的数值时用 `--dump-dom`。

### 8.3 验收纪律

- **worker 的自述不等于事实**：必须亲眼看 diff、亲自重跑测试与构建、核对产物时间戳晚于源码。
- **禁止 `git checkout` / `git stash` / `git restore` / `git reset`**：工作区有在途未提交改动，这类命令会直接毁掉它们。宁可少拿一个对比基线，也不冒这个险。（本轮改用「运行时切换属性」拿因果证据，正是这条禁令逼出来的更好方法。）
- **禁止 worker 用 PowerShell 读改写源码**（第七轮真踩过）：`Set-Content` 不带 `-Encoding utf8` 会按系统 ANSI/GBK 编码，把中文注释**永久损坏**成乱码（有损不可逆），且**测试与构建完全发现不了**。改源码一律用文件编辑工具；**每次改完立即对该文件 `git diff` 自查**，中文变乱码立即停止并报告。检测器：某行 `encode('gbk')` 与结果 `decode('utf-8')` 双双成功即高度疑似乱码。修复法：排除注释行确认相对 HEAD 的功能性差异只有预期那几处，再从 `git show HEAD:<file>` 重建并重新施加。
- **不许写假测试充数**：jsdom 没有真实布局，几何类行为测不出来就明说「单测覆盖不到，已由浏览器实测覆盖」。
- 报告必须包含**没验证 / 不确定的部分**；发现自己的探针有 bug（如分类器误判、基线取错位置）要主动更正并说明。
- 临时脚本与产物放系统临时目录，用完删除；验证用的 dev server 与无头浏览器进程用后回收。
- **采样时机**：切回页面的逐帧采样必须**从切回的那一瞬间开始**（不要先等待）——本项目两次因采样太晚漏掉真 bug；且要在**列表中段**测，最顶端（`scrollTop=0`）测不出回中段的位移。

### 8.4 编排侧经验

**provider 失败分三类，处置方式不同**：

| 类型 | 典型报错 | 处置 |
|------|---------|------|
| 容量/瞬时 | `Selected model is at capacity`、`503 price temporarily unavailable`、`Reconnecting... 5/5` | **先重试**，往往就能跑通 |
| 个人额度 | `403 Codex rolling spend limit exceeded ... $15.00 in the last 3 hours` | 重试无用，等窗口滑出（报错会给秒数） |
| 站点额度 | `403 本时段全站额度已用完，请在今天 15:00 后再试` | 重试无用，等指定时间或换模型 |

- 判断 worker 是否真的死了，看 `workerStatus` 与 `updatedAt` / `historyTotal` 是否仍在增长，**不要仅凭 `lastResult` 的旧错误就重复派发** —— 那会排队重复任务与在跑的工作打架。
- 传输中断但 worker 仍活着时，用 `agent_send_force`（restart + send，保留上下文）续投；worker 已有上下文时只发简短续做指令。
- **不要为了「提醒」而唤醒已空闲的 worker**：这会再次消耗 provider 额度，而任务若已完成则毫无收益（本工作流真踩过，直接触发了 403 超限）。约定要在派活时一次性写进简报；只在 worker 仍在跑、且提醒能改变其当前行为时才补发。
- **长任务容易超时**：本工作流有两次 worker 跑满 90 分钟被 watchdog 杀掉（`running > 5400s`），**代码其实已写完，白死在验证环节**。因此简报里要写明时间纪律（先出结论、单环节失败两次就换做法或先报告），必要时**拆成小任务分批派**。
- **换 adapter 必须新建 session**：`deepseek-v4.1-flash` 属于 cbc，codex 里没有该模型；普通 session 不能中途换 adapter。原 worker 无实质产出时，新建 session 重发简报比 `session_handoff` 更干净。
