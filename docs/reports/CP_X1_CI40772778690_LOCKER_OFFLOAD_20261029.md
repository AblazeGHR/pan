## Candidate and limits

The only product changes are in `packages/interactions/api.py::register`: its two existing `message_read` and `mark_read` handlers call a private helper. The helper queues writes on one application-instance asyncio lock, then invokes the complete existing `get_store()` construction and original store method in `asyncio.to_thread`. Thus the SQLite connection, schema check, original `BEGIN IMMEDIATE`, per-item authorization, FULL durability, row update, commit and close all occur in the same worker thread; no SQLite connection or transaction is held across an await. The handler returns its original body only after that work succeeds, and retains its original `InteractionError` mapping. Neither original route emits a read broadcast; none was added. There is no schema, batch, ledger, worker, shared executor or durability change.

Only one of these writes per app is admitted to the thread at once; other requests wait asynchronously rather than tying up a pool of SQLite contenders. A task cancelled while queued is cancelled before execution. Once admitted, request cancellation leaves the slot owned until the real thread finishes; the response is unknown to that caller, never converted to success or retried. A detached thread failure is logged. Other processes or other code paths can still contend for SQLite, and user authentication retains its original behavior.

**This offload is necessary for event-loop responsiveness but is not sufficient proof of the remote 5-second outcome.** It neither shortens FULL commits nor reduces the 113 required writes. The slow 3.12 storage tail may still exceed the original deadline even without event-loop starvation. Measure the exact candidate on MA's Windows 3.12/3.14 targeted run; preserve any residual failure and its per-ID outcomes. No increase of the original 5 seconds, optimistic read, weaker assertion or automatic retry is proposed.
