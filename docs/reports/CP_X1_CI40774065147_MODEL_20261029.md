The `other` label is a diagnostic caller category, not a new product metric: source and event order show one constructor transaction preceding each observed read transaction. It includes connection, `BEGIN IMMEDIATE`, schema checks and close. It is substantially smaller than the read transactions in these traces. A per-ID read transaction also includes its owner/recipient lookup, update and result projection; the separate cost of authorization itself is **not** measured. ASGI-to-first-database combines authentication, the bounded slot, scheduling and thread entry; it does not isolate slot wait. Browser-to-DOM observations include event scheduling and observer overhead, not just React CPU. The 3.12 monotonic clock in these artifacts is coarse (many 0/15/16 ms intervals), so small individual values are quantized. None of these sums implies unobserved requests completed.

## Decision and constraints

Repeated constructor initialization is **not the dominant measured cost**, so the condition for the proposed cache optimization is not met. This candidate makes no product or fixture change. On this evidence, eliminating at most the observed constructor intervals would not establish the original deadline for all 113 items; remaining unobserved transaction times and UI convergence are unknown. A cache would also need to bind the trusted resolved profile/root and current factory, retain no principal/authorization/connection, and correctly invalidate on file removal/replacement or corruption. Merely caching a Python object by pathname could bypass initialization after a database replacement or reuse a store across a changed profile/factory. Those boundaries cannot be assumed away.

There is a concrete model/acceptance conflict to resolve: 113 individually authorized, individually committed `synchronous=FULL` SQLite writes on a single bounded writer have completion time dependent on storage latency, while the existing real-browser assertion requires the whole UI to converge within a fixed five-second window. The observed completed writes already occupy most of that interval; an unbounded filesystem commit cannot provide a universal five-second guarantee. Thread offload preserves event-loop availability but cannot make FULL durable writes faster by itself. The measured result does not prove every target machine will fail, nor that the UI is correct for missing observations.

Within the present scope, the useful next decision is whether the target environment can provide an explicit durable-write latency budget sufficient for the existing assertion, or whether MA/user will authorize a specific product/acceptance change and its semantics. Any transaction consolidation, batch endpoint, database/schema/global cache change, weaker FULL durability or modified threshold would exceed the current boundary and requires its own review; no such change is made here. Further remote reruns of unchanged code would not answer this decision.
