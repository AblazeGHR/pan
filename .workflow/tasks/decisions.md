# 决策方案附件

> 本文件保存决策的证据、选项和技术说明。当前是否阻塞、用户下一动作和最终结论只以 `../overview.md` 的决策卡为准。

## DEC-001：文件复制/拖入输入框

- 方案概括：确定文件复制/拖入支持普通文件、拒绝目录，并以结构化 AttachmentRef/parts 统一附件身份和兼容旧协议。

- 最终结论：采用 A + C。第一阶段支持普通文件复制/粘贴和拖入，目录明确拒绝；同时采用结构化 `AttachmentRef` / `parts` 协议，兼容旧 text/Markdown 协议。
- 事实：浏览器系统文件复制/拖入通常提供 `File` / `FileList`，不应依赖客户端绝对路径；目录需要额外的 handle/entry API，兼容性和复杂度更高。
- 方案 A：普通文件复制/粘贴和拖入，目录拒绝；复用现有上传接口和 Markdown 校验。
- 方案 B：普通文件和目录递归上传；需要目录枚举、相对路径、批量进度、取消、部分失败和浏览器 fallback。
- 方案 C：结构化 `AttachmentRef` / `parts`；统一客户端文件、服务端文件和消息附件的 session-scoped opaque `attachmentId`。
- 后续边界：目录递归上传另立任务；T-026 的路径表示修复不改变本决策。T-025 已承接本决策形成的正式实现。
- 来源：开发者会话与用户 2026-09-13 的“A+C”确认。

## DEC-002：输入框、跨 Session 附件与发送事务

- 方案概括：确定附件待发送状态按 Session 隔离、正文文件引用可合法复用，并让发送具备立即清空、乐观显示和失败恢复语义。

- 最终结论：待发送 chip、输入框内附件节点不得跨 Session；对话正文中渲染出的文件路径/editor 链接可以跨 Session 拖入，并复用经服务端校验的文件引用；Send 立即清空并乐观显示，失败恢复一份可编辑副本。
- 文件语义：服务端文件使用实时路径；客户端文件只在上传阶段作为浏览器 `File`，上传后统一按服务端文件处理；复制的图片/HTML 文件保持原文件上传，网页富文本转安全纯文本。
- 边界：目录或目录混合拖入整批拒绝；同一资源可在一条消息中出现多个 occurrence；浏览器不暴露或信任客户端绝对路径。
- UI/协议：editor/download href 只是 UI 投影；Worker 文本由服务端解析为实际路径；跨 Session 正文文件链接必须经过权限和引用校验。
- 影响任务：T-027、T-027.1、T-027.2；T-031 与 T-037 提供真实隔离验证和缺陷修复证据。
- 来源：用户会话 2026-09-15。

## DEC-003：报告与任务身份的最小继承规则

- 方案概括：确定任务身份在入队时显式继承并随 Worker/report 传递，避免通过历史消息猜测报告归属。

> 已由用户决定，作为 T-040 的实现依据；不再作为待决策入口。

- 状态：已决定；来源/时间：用户明确回复“按照这个原则推进”，2026-09-17。
- 结论：正式任务使用稳定 `taskId`；普通 `agent_send` 不需要独立业务编号，入队时继承目标 TA 当前任务的 `taskId`；Worker 执行哪条输入，report 就回传该输入携带的 `taskId`。
- 无任务上下文时：普通消息允许 `taskId=null`，不错误继承旧任务。
- 不实施：`sourceQueueItemId`、`deliveryUnitId`、完整事件模型；`queueItemId` 仅作为队列内部技术 ID。
- 约束：不得在 report 生成时通过历史“上一条/最近任务”猜测归属；归属必须在输入入队或 Worker 领取时确定，并可在重启/恢复后保持。
- 承接任务：T-040；T-032 保留调查事实与证据，不再等待第 2 档选择。
- 关键来源：`packages/core/worker.py` 报告与队列逻辑；`packages/mcp/server.py` 的 `agent_send`；具体调查记录见 T-032 详情。
