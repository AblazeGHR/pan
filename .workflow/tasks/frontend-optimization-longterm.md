# T-062：前端性能与状态新鲜度长期优化

> 本文件记录长期项目边界和阶段入口；每个实现、调查、测量或回归阶段另立子任务，完成后再回填 overview，不把长期项目写成一次性“大重构”。

## 当前状态

- 状态：已立项，用户暂停，未启动。
- 启动条件：用户明确说“启动”或给出等价授权。
- 暂停期间：不派 TA、不创建 worktree、不启动隔离服务、不执行 E2E 或产品代码修改。

## 任务概括

让用户打开 Manage、切换 Session、发送消息或观看流式回复时看到及时且可信的实际状态，消除陈旧缓存伪装成当前状态、页面卡顿和长时间无反馈问题，并建立可持续的前端性能回归能力。

## 当前现象

- 打开 Manage 后要等待很久才显示实际情况；界面会先展示一个无法判断时间的新旧状态的缓存值。
- 最近多个前端区域出现卡顿、延迟或状态长期不收敛，问题不局限于单一页面或单一组件。
- 现有 T-052/T-053 已覆盖一批发送延迟、Session 卡片、流式 delta 和终态状态问题，但不能视为长期性能治理已经完成。

## 已确认事实与待验证假设

- 已确认事实：当前前端存在本地状态、HTTP 快照、WebSocket 事件和组件挂载刷新等多种状态来源；它们的时序和新鲜度需要按页面逐一测量。
- 初步现象：Manage 首次打开可能使用旧缓存，并在权威数据返回前缺少明确的 loading/stale 语义。
- 待验证假设：缓存读取、请求串行化、全量 store 更新、组件重渲染、WS 断线补偿或后端快照生成中的一个或多个环节造成延迟；在测量前不预设唯一根因。

## 项目目标

1. 状态可信：旧缓存不能无标签地伪装成当前实际状态；若先展示缓存，必须有明确 stale/loading 语义并在权威数据到达后收敛。
2. 交互及时：Manage 打开、Session 切换、发送、流式输出、完成指示灯和 Session 卡片更新有可测量的响应预算。
3. 渲染稳定：长历史、高频 delta、多 Session 和后台恢复不会造成明显长任务、重复请求或全量无效重渲染。
4. 生命周期完整：WS 重连、focus/visibility、worker 完成、失败、重启和快照竞态都能最终收敛。
5. 可持续回归：为关键路径保留真实浏览器基线、性能时间线和最小回归集，后续优化不依赖主观感受。

## 分阶段计划

### Phase 1：测量与复现

- Manage 打开：记录缓存读取、首屏 loading、首次实际数据、最后一次权威数据和可交互时间。
- Session/聊天：记录发送→用户消息、首个 delta、最后 delta、result、idle、卡片 lastmsg/count 的时间线。
- 生命周期：覆盖快速切换 Session、重复打开 Manage、focus/visibility、WS 重连、worker running/done/failed 和后台标签页。
- 输出：按请求、事件、store 更新、React commit、可见 DOM 和长任务分段的证据；区分本地缓存快、权威数据慢和 UI 渲染慢。

### Phase 2：状态新鲜度与数据协调

- 为缓存、快照、WS patch/事件和当前 UI 建立明确的来源优先级、revision 或时间戳语义。
- Manage 首次打开采用明确的 loading/stale/ready 状态，不把未知新鲜度的数据直接显示为当前事实。
- 处理旧 HTTP 响应、旧 WS 事件、切换 Session 和重连恢复，避免旧状态覆盖新状态或状态永远停留在旧值。

### Phase 3：请求与渲染性能

- 根据 Phase 1 证据减少重复 GET、全量 snapshot、整店订阅和无效组件重渲染。
- 对 Markdown、流式 delta、长历史、tool/thinking 块和 Manage 大列表设置批处理、memo、虚拟化或分层渲染边界。
- 任何优化必须保留消息顺序、Session 隔离、附件/草稿、未读状态和终态持久化语义。

### Phase 4：生命周期与异常路径

- 覆盖静默失联、半开 WS、重连、服务端慢响应、worker 退出、queue recovery、通知失败和页面恢复。
- 明确“显示缓存”“等待权威数据”“重试”“失败”各自的用户可见行为，不以点击 Session 作为唯一补偿刷新。

### Phase 5：持续基线

- 保留真实 Chromium 的关键路径探针和低成本合成压力测试。
- 每个子任务记录改前/改后：首个可见时间、最终收敛时间、请求数、长任务、帧间隔、状态回退次数和错误率。
- 共享前端状态、WS 协议、Session/Worker 生命周期或持久化语义发生变化时，按风险触发定向回归，不默认重跑全部测试。

## 第一阶段 Manage 验收动作

1. 在隔离服务中准备一个已知服务端状态与一个可辨识的旧缓存状态，打开 Manage。
2. 记录从点击打开到 loading、首次显示、权威数据返回和可交互的时间；同时观察是否把旧缓存标为 stale/loading。
3. 在请求尚未返回期间改变服务端状态，再重复打开、关闭、快速重开 Manage。
4. 预期：旧缓存不能无标识地冒充当前实际状态；页面应明确显示加载/过渡状态，并在权威数据返回后显示新状态；旧响应不得覆盖新响应；重复打开不能长期停留在旧值。
5. 进一步执行 Session 切换、focus/visibility 恢复和 WS 重连，预期 Manage 与 Sidebar/Chat 的状态最终一致。

没有真实隔离服务或浏览器证据时，记录为“未验证”，由阶段 TA 提供可复现探针和证据入口，不把代码审查或单元测试写成 Manage 行为通过。

## 交付与边界

- 这是长期项目，不要求一次性重写前端或一次性解决所有卡顿。
- 每个子任务必须有独立任务概括、范围、指标、证据、未验证项和回滚边界。
- 不改变 8768；真实 E2E 使用独立端口和独立配置。
- 不把 provider 慢、后端队列慢、桌面通知可见性或 OS 文件行为未经测量地归因给 React。
- 不以“缓存命中”作为性能通过标准；必须同时证明数据新鲜度和用户可见收敛。
